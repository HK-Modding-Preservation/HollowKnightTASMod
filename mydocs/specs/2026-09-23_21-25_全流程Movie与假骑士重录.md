# SDD Spec：从启动第 0 帧开始的全流程 Movie 与假骑士重录

> 状态：INNOVATE / LOCKED。本文记录当前代码实证、用户约束与候选架构；第 3 节须在 PLAN 阶段形成接口和执行清单。本阶段按 SDD 规则不实施代码修改。

## 0. Open Questions (MUST BE CLEAR BEFORE CODING)

- [ ] **统一帧坐标**：新 Movie 的第 0 帧明确是 D06 原生 PlayerLoop 尚未执行的暂停点。后续应逐个原生 PlayerLoop 计数，还是在不产生可采样游戏输入的阶段用有长度的启动／载入段表示？两者都必须给 Studio 一个从 0 开始、跨标题与读档的连续可定位坐标，且不能把旧版局内 `input` tick 直接重命名。
- [x] **菜单操作语义（用户决定）**：标题菜单与局内一样记录并回放真实游戏输入，不以“选第 N 槽”等高层命令替代操作；人工和 AI 共用同一输入路径。
- [x] **存档绑定及安全（用户决定）**：Movie 不绑定存档或槽位；用户自行保证同一菜单位置指向同一存档。Mod 必须保证不会修改用户的存档；具体隔离／写入拦截机制仍须在架构设计中确定。
- [x] **假骑士新示范的起点（用户决定）**：从游戏启动第 0 帧开始，以真实菜单输入加载现有诸神堂存档并击败假骑士；示范本身无需从空槽新建档。
- [x] **鼠标模式（用户决定）**：Studio 设置中可启用／禁用游戏鼠标输入；禁用时游戏不得响应鼠标移动、点击或鼠标绑定的动作，菜单可纯键盘操作。Studio 界面仍须能用鼠标操作。
- [ ] **兼容门禁**：现行 manifest 把分辨率／窗口模式、TAS 组件及 Mod 集合等一并哈希，导致仅改变显示模式也拒绝导入。新协议应明确强制条件、可验证警告及终态校验的分层；不得改写旧 Movie 哈希来伪造兼容。

## 1. Requirements (Context)

### 1.1 Goal

Movie 是从受控游戏启动第 0 帧开始的**完整过程**。玩家经 Steam 启动游戏后，Studio 自动打开并停在第 0 帧；可在此打开已有 Movie 或创建新 Movie，然后仅用 Studio 的逐帧／播放控件，以真实游戏输入复现标题菜单、选存档／新建存档、局内操作、Save&Load、返菜单和多个存档间切换。Movie 不与某一个存档或槽位绑定；相同槽位／存档内容由用户保证。Mod 必须保证用户原始存档不被修改。

### 1.2 In-Scope

- 定义与持久化新版本完整序列，保留旧 v1 局内 Movie 的明确读取／迁移语义；旧记录不得被默认为全流程序列。
- 第 0 帧加载／新建、逐帧、播放、暂停、停止及跨启动门闩到 Runtime 的无缝接管；Studio 显示统一位置与当前阶段。
- 标题菜单及局内输入、场景切换、创建存档、读档、返菜单、Save&Load 与多槽切换进入同一时间线；支持可编辑、可校验、可回放、可检查的顺序和边界。
- Studio 设置提供游戏鼠标输入开关；关闭时游戏所有阶段忽略鼠标，键盘仍可完成标题菜单与选槽，Studio 自身仍接受鼠标；开启时真实鼠标输入应纳入同一时间线的录制与回放。
- 不把存档内容或槽位标识写成 Movie 的绑定条件；回放期间创建档、存档、读档或多槽切换对游戏可见，但不能修改用户原始存档。验证中记录原始存档测前／测后身份。
- 按新规则生成一份独立假骑士示范：从启动第 0 帧开始，真实输入在标题菜单加载现有诸神堂存档，不要求玩家手动预选；完整回放后验证原生 Boss 死亡事件及输入／语义差异报告，并保留旧归档原件。
- 更新 Studio 操作手册、CURRENT、所需的 CLI／静态检查与定向自动化；稳定后执行一次必要的实机 smoke，不重跑无关历史矩阵。

### 1.3 Constraints / Non-goals

- 正常 TAS 保持原版玩法与菜单语义；不得靠写入 Hero、FSM、敌人或资源状态跳过玩家操作。人工和 AI 共用控制路径。
- 旧假骑士 `fixtures/t16/false-knight-ea42-3042.hktas` 的第 0 帧是加载第 4 槽并建立局内语义基准后的首个 `input` tick；它不是进程启动帧。其 3043 个输入样本只能作为战斗段参考，不能宣称已满足新规则。
- D06 的 `Startup frame: 0` 是第一个原生 PlayerLoop 前的门闩；当前没有 Runtime IPC／可用 `HeroController`。直接打开旧 `.hktas` 只可查看，不能从此点上传并播放。
- 当前最小 Mod 环境仅启用 HollowKnightTAS；其余 Mod 在游戏安装的 `Mods/disabled`。重新生成时需记录实际安装身份，避免把已有的改 manifest 测试副本当作正式新示范。
- 不覆盖用户存档、旧 Movie、旧交付包或仍被引用的证据；不凭旧 VERIFIED 状态推断新协议通过。

### 1.4 Research Findings (2026-09-23)

1. v1 文本的固定头包含 `manifest-sha256` 与 `baseline <id> <sha256>`，唯一展开输入命令 `frames` 的单位是 InControl 已提交的 `input` tick；菜单／载入帧不在展开长度中。`MovieParser` 命令仅有 `frames`、`marker`、`checkpoint`、`assert`。
2. 既有生命周期能力位于 Movie 外的 `ReplayLifecycleLog`／`MovieLifecycleExport`：只允许 `ReturnToMenu`、`LoadSlot`；以局内 `AfterMovieTick` 和输入前缀哈希定位边界，记录 `NativeFrameCount`，但这些帧不成为 Movie 输入帧。`BaselineBundle` 必有 `OriginalSlot > 0`。`RuntimeReplayJournal.OnNewGame` 明确使生命周期回放失败；首次选槽前的加载也只是在建立首个局内基准，不属于 Movie。
3. D06 启动门闩在原生 `PlayerLoop` 调用点暂停，Studio 的 `StartupBootController` 通过共享状态逐帧放行；门闩与 Runtime IPC 独立。Studio 当前仅在这个阶段显示 `Startup frame`，随后切回局内 `Frame`。
4. `RuntimePauseController.Pause()` 一般要求 `GameState.PLAYING`；标题菜单专用暂停只用于冷恢复。局内输入适配器只覆盖 Hero actions；`NativeLifecycleInputLease` 在原生菜单／读档期间有意不合成输入边缘。完整菜单输入与标题阶段的受控暂停仍需设计和实机验证。
5. `DesktopSaveSlotBaselineProvider` 已有目标槽字节复核、覆盖许可和备份机制，可复用其安全原则；现有 Restore 则从标题菜单安装单槽基准并加载，仍以局内单槽根为中心。
6. 旧示范在最小 Mod 环境和匹配第 4 槽起点下，使用仅替换 manifest 行的**测试副本**曾实机回放至假骑士死亡且 `mismatchCount=0`；这仅证明旧战斗输入可供重录参考，不是从启动帧开始的新序列，也不是旧原件原样兼容。证据见 `CURRENT.md` 与 `artifacts/false-knight-compat/manual-ui-result.json`。
7. HK 的主菜单输入适配器可绑定 `InputHandler.inputActions` 中的 `moveVector`、`menuSubmit`、`menuCancel`、`jump`、`attack`、`cast`；但更早的 `PreMenuInputModuleActionAdaptor` 和 `InputModuleBinder` 各自创建独立的 `PlayerActionSet`。UI 输入模块还可单独消费 Unity 鼠标位置／按键。现有 TAS `HeroActionRecorder` 和 `HeroInputAdapterBase` 只覆盖 11 种局内 action，缺少菜单确认／取消、独立菜单动作集和鼠标，因此仅延长旧 `frames` 不能录全菜单。出处：hk-api `hkapi/HeroActions.cs:10`、`hkapi/InputModuleActionAdaptor.cs:16`、`hkapi/PreMenuInputModuleActionAdaptor.cs:13`、`hkapi/InputModuleBinder.cs:13`、`hkapi/InControl/HollowKnightInputModule.cs:82`，以及本项目对应输入类。
8. `GameManager.SaveGame` 先直接创建／轮转 `userN.modded.json(.bak)`，再经 `Platform.Current.WriteSaveSlot` 持久化主槽；`DesktopPlatform` 可能转给在线存档子系统，或写 `Application.persistentDataPath` 下的本地槽位并产生 `.new`、版本副本及备份。只拦截主槽 API 或事后恢复 `userN.dat` 均不满足“Mod 不修改用户存档”。出处：hk-api `hkapi/GameManager.cs:2394`、`:2412`、`:2448`、`:3349`，`hkapi/DesktopPlatform.cs:139`、`:190`、`:301`。HK 技能的来源事实已记录于 `rules/evolution-notes/20260923_214819_hk-title-menu-input-and-desktop-save-slot-call-paths-for-tas.md`、`rules/evolution-notes/20260923_215019_hk-modded-sidecar-save-path-and-savegame-write-order.md` 与 `rules/evolution-notes/20260923_215425_hk-pre-menu-action-sets-and-mouse-input-for-tas-capture.md`。
9. HK 的 `HollowKnightInputModule` 和 `InControlInputModule` 都有公开的 `allowMouseInput`，可关掉 UI 指针移动／点击处理；但动作集里的 `MouseBindingSource` 仍可能触发攻击等动作，须另行隔离，才能满足“禁用后游戏不响应鼠标”。出处：hk-api `hkapi/InControl/HollowKnightInputModule.cs:82`、`:123`、`:329`，`hkapi/InControl/InControlInputModule.cs:112`、`:592`，来源事实已记录于 `rules/evolution-notes/20260924_072824_disable-hollow-knight-game-ui-mouse-without-disabling-keyboa.md`。

## 2. Architecture & Strategy

### 2.1 方案比较

| 方案 | 具体做法 | 收益 | 代价／结论 |
| --- | --- | --- | --- |
| A：在 v1 前补启动段，继续使用旁路生命周期日志 | 旧 `frames` 仍按局内 InControl tick 计数；新增菜单段与“载入槽”事件，两个坐标在 Studio 拼接显示 | 可复用最多旧 ReplaySave 代码 | 菜单输入与局内输入仍非同一录制逻辑；载入等待不占统一帧；选槽易退化为高层命令。**不满足本次约束，不选。** |
| B：v2 原生帧时间线 + 统一真实输入录制／回放 + 存档写时复制 | 启动门闩的已完成 PlayerLoop 数作为全程帧序号；每个原生帧关联 0..N 个实际游戏消费的输入样本，覆盖 HeroActions、独立预菜单动作集，并按 Studio 设置启用／屏蔽游戏鼠标。菜单与局内共用捕获、注入、边缘校验的时间线，生命周期只作观察／诊断。启动时把原始存档只读复制到会话私有空间，所有 TAS 会话读写落在该副本 | 真正从启动 0 帧逐帧定位；真实菜单输入与局内相同；Movie 不绑定槽位；能保留新建档和 Save&Load 的真实游戏行为，原始存档不改写 | 需改 Core 协议、原生／托管帧计数交接、菜单暂停和输入适配；必须完整覆盖主槽、Mod 侧文件及旧恢复路径。**推荐。** |
| C：从启动起录制／注入 Windows 键盘、鼠标、手柄事件 | 可在托管输入系统出现前记录物理设备 | 依赖焦点、键位布局与设备身份；和现有 `HeroActions` 局内录制路径不同，难以保证同一帧的游戏输入语义。**不选。** |

### 2.2 推荐方案 B 的核心契约（待用户 `Selected`）

1. **统一时间线**：Movie 帧 0 是首个原生 PlayerLoop 执行前的等待点；每完成一个 PlayerLoop，位置加 1。每帧记录零个或多个在该循环内被游戏消费的输入样本；确实没有可消费输入的早期启动帧为零样本。菜单、场景加载、局内及返回菜单都占据真实帧位置；逐帧只放行一个 PlayerLoop。对一帧内样本数量／次序的任何偏差立即报告，不静默补帧。旧 v1 的 `input` tick 坐标保持旧语义，另设显式导入／转换路径。
2. **同一输入管线**：扩展现有录制器、绑定租约和播放注入器，统一记录游戏当帧实际消费的动作状态／边缘；适配同一 `HeroActions` 的主菜单与局内、预菜单独立 `PlayerActionSet`，并在鼠标启用时纳入 Unity UI 鼠标位置／按键。动作至少覆盖菜单移动／确认／取消、暂停与现有局内按键；完整名单在 PLAN 前以实际消费路径核定。菜单选槽、建档、Save&Load 均由真实输入触发；Movie 正文没有 `LoadSlot(4)` 或 `CreateSave` 之类的替代命令。观察到的槽号可放诊断证据，不成为 Movie 头的要求。
3. **门闩交接**：Studio 在启动帧 0 即可新建／打开并准备 v2 Movie。原生门闩在 Runtime 尚未连接时管理逐帧与全局计数；一旦 Runtime 有稳定输入通道，按经过验证的边界接管输入注入和菜单／局内暂停。交接不能遗漏、重复或暗中推进帧；若某个可操作菜单帧早于输入通道可用，则暂停并明确失败，不能放任物理输入混入。需要定向实机探针测出 PlayerLoop 与 InControl 更新对应关系，再在 PLAN 锁定具体握手。
4. **存档保护**：启动器／原生层必须在允许第 0 帧播放前建立保护边界；受控 TAS 进程仅读取原始四槽相关文件，创建限额、私有的会话副本。游戏的槽位存在判断／读取／写入／清空以及 `GameManager.ModdedSavePath` 直接侧文件访问统一指向该副本；Save&Load 和多槽切换看到同一副本的最新内容。托管层安装后还需核验重定向仍有效；旧 ReplaySave 安装／回退路径在全流程会话中也只许访问副本，否则拒绝。副本不自动写回。不能用“先写原件、结束后还原”的方式满足保护要求。若无法证明首帧前保护已生效、平台采用未覆盖的在线存档或第三方 Mod 可直接写原始存档，受保护会话必须在继续前失败，不降级到原件写入。
5. **格式与兼容**：v2 去掉强制单槽 `baseline <id,sha>`；Movie ID 仍来自规范化正文。`gameVersion`、Mod 列表和显示设置等可保留为录制环境信息，但一般差异先给警告和运行时偏差证据；协议、动作表、时钟／启动门闩能力缺失必须拒绝。旧 v1 原样可读、原样受旧门禁约束，不能改头哈希冒充 v2 或把局内第 0 tick 标成启动第 0 帧。
6. **假骑士新示范**：在仅启用 TAS Mod 的受保护会话，Steam→Studio 第 0 帧→真实菜单输入选择现有诸神堂存档→进入假骑士战斗→击败 Boss；另存 v2 Movie 与会话证据。验收包含新 Movie 从启动 0 帧完整播放、无人工选槽、原始存档路径写入审计为零且测前／测后文件身份一致、录制／回放输入偏差为零、原生 Boss 死亡事件成立。旧 3042 帧战斗段只能参考，不能简单在前面拼菜单文本后声称已重录。
