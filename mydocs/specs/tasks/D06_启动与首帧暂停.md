# D06：自动启动 Studio 与启动首帧暂停

## 用户目标

1. 直接启动游戏，由 Mod 自动打开 Studio 后即可正常控制。
2. 游戏启动时自动暂停在第一帧，保持 libTAS 的启动操作习惯。
3. 安装后验证以上功能，以及继续、逐帧与正常退出。

## 已确认的缺口

- `RuntimeCompanionService.Start` 会自动打开 Studio，但没有给普通启动加载外部时钟。
- `VerifiedGameLauncher.LaunchRunAsync` 已有受控启动入口：创建新进程并由 ClockInjector 早期加载 ClockBridge；目前仅 Studio 启动和冷恢复使用它。
- `RuntimePauseController.PauseCore` 默认只接受 PLAYING，专用菜单暂停仅服务冷恢复。
- `RuntimeControlService.Pause/Step` 还要求录制起点就绪，启动菜单没有这一条件。
- ClockBridge 的 `clock_worker` 等待 PayloadReady，Runtime 仅在 `Menu_Title` 发出该信号。因此现有托管暂停链路不能证明启动第一帧已停住。

## 实施顺序

### A. 启动前控制通道

检查 ClockInjector/ClockBridge 现有早期加载边界，选定可验证的首帧门闩。Studio 必须能在 Runtime IPC 尚未就绪时读取启动状态、继续和单帧推进，且暂停等待不能计入 Unity 游戏时间。明确原生启动帧和 Movie 输入帧的不同计数，不把标题菜单暂停伪装成进程启动首帧。

验收：游戏启动首帧保持不变；一次单步只放行一帧；继续后正常完成 Mod 初始化并转交 Runtime 控制。不得等待标题菜单后才首次暂停。

### B. 普通启动接入

让直接启动游戏也进入同一受控启动路径。优先复用现有已验证启动器；如采用自动重启移交，必须在未进入用户游戏存档前完成，绑定原进程身份，避免启动循环和重复进程，并在 Studio 显示真实阶段。已经进入局内的进程不得被自动关闭。

验收：Studio 原先关闭和原先运行两种情况均能接管直接启动的游戏；外部时钟可用；失败有明确原因且没有重启循环。

### C. 安装验证与交付

运行上述两条短启动流程，检查暂停保持、单步、继续、Runtime 接管和退出。按需增加针对启动门闩/移交的定向测试，不重复战斗矩阵。更新操作手册、签名包和 CURRENT，每阶段提交。

启动方案可能需要改变 Runtime 或时钟载荷；本次用户目标允许这类必要修改。旧存档、旧视频与现有配套包保留；身份变化后明确旧存档兼容范围，不能绕过校验。

## 原生帧探针

官方符号 `UnityPlayer_Win64_mono_x64.pdb` 与当前 UnityPlayer 匹配，GUID 为 `0334BE9063DD4644BEE1FC8D56C840C2`，age 为 1。本地文件位于 `artifacts/d06-startup`，235139072 字节；无需再次下载。`scripts/inspect_native_symbols.c` 使用 DbgHelp 校验符号匹配并查询地址。符号来源为 [Unity 官方符号服务](https://docs.unity.cn/2021.2/Documentation/Manual/WindowsDebugging.html)。

`PerformMainLoop` 的 RVA 为 `0x523030`，其中 `0x5231e5` 调用 `PlayerLoop`（RVA `0x75c4c0`），原始指令为 `e8 d6 92 23 00`。实验代码仅替换该 CALL 的目标，经附近跳板进入暂停门闩，再执行原函数；不搬移函数序言。启用时校验 PDB GUID、age 和原指令，启动器另行校验完整 DLL 哈希。不匹配即拒绝。未启用时不修改该位置。

原生探针使用环境变量 `HKTAS_BOOT_FRAME_GATE=1`，新增同 token 的 `Step` 自动重置事件、`State` 16 字节共享区。四个 LONG 分别为已完成循环数、等待标志、执行线程 ID、已安装标志。Ready 表示循环边界等待；Step 放行一次原 `PlayerLoop`，Continue 持续放行。启动阶段每次循环推进一个既有时钟步长，托管载荷采用时钟后停止原生推进，避免双重推进。该交接仍待实机确认。

## Studio 启动帧联调

Studio 现已创建 Step/State 通道，显示独立的 `Startup frame`，在没有 Runtime IPC 时执行原生单步。一次请求必须观察到新的完成计数和等待标志才允许下一次请求；Ready 的旧值不能重复放行。启动回执跨单步和继续操作保留。原有两个握手测试、两个生命周期测试及新增单步状态测试共 5 项通过，Studio 编译通过。

实测发现原生等待使游戏窗口未响应，现改为消息感知等待：暂停期间处理窗口消息，但抑制重入的 PlayerLoop，避免消息处理意外推进游戏。最新包为 `artifacts/d06-startup/frame-pump-bundle`，Bridge SHA-256 `baa4460fd70dc87d01b4fccdc320afd3961b528ff80d06c9ab1edac0d15e77c3`。开发版使用该包，不修改正式安装。
