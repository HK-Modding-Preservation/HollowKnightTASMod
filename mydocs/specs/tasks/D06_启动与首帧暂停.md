# D06：自动启动 Studio 与启动首帧暂停

## 用户目标

1. 直接启动游戏，由 Mod 自动打开 Studio 后即可正常控制。
2. 游戏启动时自动暂停在第一帧，保持 libTAS 的启动操作习惯。
3. 安装后验证以上功能，以及继续、逐帧与正常退出。

## 已确认的缺口

- `RuntimeCompanionService.Start` 会自动打开 Studio，但没有给普通启动加载外部时钟。
- `VerifiedGameLauncher.LaunchRunAsync` 已有受控启动入口：创建新进程并由 ClockInjector 早期加载 ClockBridge；目前仅 Studio 启动和冷恢复使用它。
- `RuntimePauseController.PauseCore` 默认只接受 PLAYING，专用菜单暂停仅服务冷恢复。
- `RuntimeControlService.Pause/Step` 还要求录制起点就绪，启动菜单没有这一条件。
- ClockBridge 的 `clock_worker` 等待 PayloadReady，Runtime 仅在 `Menu_Title` 发出该信号。因此现有托管暂停链路不能证明启动第一帧已停住。

## 实施顺序

### A. 启动前控制通道

检查 ClockInjector/ClockBridge 现有早期加载边界，选定可验证的首帧门闩。Studio 必须能在 Runtime IPC 尚未就绪时读取启动状态、继续和单帧推进，且暂停等待不能计入 Unity 游戏时间。明确原生启动帧和 Movie 输入帧的不同计数，不把标题菜单暂停伪装成进程启动首帧。

验收：游戏启动首帧保持不变；一次单步只放行一帧；继续后正常完成 Mod 初始化并转交 Runtime 控制。不得等待标题菜单后才首次暂停。

### B. 普通启动接入

让直接启动游戏也进入同一受控启动路径。优先复用现有已验证启动器；如采用自动重启移交，必须在未进入用户游戏存档前完成，绑定原进程身份，避免启动循环和重复进程，并在 Studio 显示真实阶段。已经进入局内的进程不得被自动关闭。

验收：Studio 原先关闭和原先运行两种情况均能接管直接启动的游戏；外部时钟可用；失败有明确原因且没有重启循环。

### C. 安装验证与交付

运行上述两条短启动流程，检查暂停保持、单步、继续、Runtime 接管和退出。按需增加针对启动门闩/移交的定向测试，不重复战斗矩阵。更新操作手册、签名包和 CURRENT，每阶段提交。

启动方案可能需要改变 Runtime 或时钟载荷；本次用户目标允许这类必要修改。旧存档、旧视频与现有配套包保留；身份变化后明确旧存档兼容范围，不能绕过校验。

## 当前状态

已实现 A 的底层握手：`startup_gate.h` 在显式启用时阻塞首次 Unity 主线程 QPC 调用，Studio 的 `StartupBootGate` 使用独立事件接收回执和放行。等待发生在时钟调用中，DllMain 只打开句柄；等待不会消耗后续载荷初始化超时。控制端退出会释放等待。`VerifiedGameLauncher.LaunchInteractiveAsync` 接受可选 gate，默认启动/冷恢复清除继承的 gate 环境变量，避免意外再次暂停。

原生握手测试通过（缺省不启用、非法参数拒绝、真实阻塞和放行、仅进入一次）；桥接 DLL 编译通过；Studio 两项定向测试通过（回执、释放、实例隔离）。产物仅在 `artifacts/d06-startup`，尚未替换安装版本。

下一步：把 gate 生命周期、状态和继续操作接入 Studio，再用受控启动验证实际 QPC 停点是否早于首帧。QPC 调用不等于帧边界；当前不具备逐帧放行能力，也不能据此宣布首帧目标通过。随后补启动帧步进与 Runtime 交接、普通启动接管并短实测。现有 D05 配色/手册版本保持已交付状态。
