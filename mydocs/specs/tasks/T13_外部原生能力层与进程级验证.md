# Task Spec T13: 外部原生能力层与进程级验证

- **Status**: REOPENED_BY_T24
- **Gate**: G4 Native Capability
- **Depends On**: T07, T12
- **Produces**: 签名 Windows x64 NativeHost、能力目录、构建白名单、原生能力逐项验收报告与 Runtime/T09 自动回退；T24 新增统一虚拟时钟 Bridge/Payload 候选，未通过前不得标记 verified

## 0.1 T24 Reopen Evidence (2026-08-02)

T24 的真实游戏差分已经证明：在原始 `targetFrameRate=400`、
`captureDeltaTime=0` 环境中，同一 1200-tick 输入的连续无 TAS 路径产生 257 个
fixed step，而逐次单帧路径只产生 141 个。后者把起椅从 tick 357 拖到 tick 638，
导致攻击和快速二段跳输入到达时 Hero 尚未恢复原版控制。输入本身 1200/1200
完全一致，且未使用 gameplay mutation，因此剩余首差异属于时钟/调度环境。

只改 Windows PlayerPrefs 的帧率值也已被负对照淘汰：进程启动后仍报告
`Application.targetFrameRate=400`、`Time.captureDeltaTime=0`。T13 因此重新进入
实验，新增固定构建、固定路径、签名包内的
`native.clock.override.experimental.v1`。它必须把同一时钟环境同时施加于无 TAS
reference 与 TAS candidate；若只能改变 TAS 路径，T24 仍为 FAIL。

## 0.2 Cold-Restore Boundary (2026-09-01)

T24 已证明同一 Unity 进程内返回标题并重放不能回退绝对 `Time.time/fixedTime`。T09/T21
因此采用“全新进程 + baseline + canonical prefix replay”的轻量方案。该方案不是
`native.checkpoint`：T12 负责跨进程监督，T09 负责 intent/存档/重放；本任务只负责提供一个
reference 与 candidate 对称、启动前生效、精确 build/hash 绑定且已经通过 T24 的 startup clock
profile。现有 v11 测试 bundle 证据不能自动提升为发布 capability；未完成签名发布、负控和双进程
验收前，产品必须报告 `unsupported`，不得用晚注入或真实墙钟启动替代。

## 0. Open Questions

- None 阻塞基础设施实现。每个原生 capability 的可支持性由本 Spec 的独立实验决定；未知结果必须保持 `unsupported`，不能靠猜测补全。

## 1. Requirements

### Goal

当纯 Runtime Mod 无法安全完成输入边界、原生时间观测、高质量捕获或同进程**进程级**即时 checkpoint 时，开发一个由 T12 Companion 自动启动的 Windows 用户态 NativeHost，并在确有必要时加载固定、签名的 NativeBridge。T14 的 room-entry 语义关键帧是更轻量、纯 Mod 的独立路线，不要求先完成或启用本任务。

NativeHost 不取代 Runtime：

- Runtime 仍是 HK 语义、safe tick、输入和确定性判定的唯一权威。
- T09 仍是任意/定时、跨启动选择 savestate 的保证。
- T14 若通过可优先提供持久化语义关键帧加速；本任务的 native checkpoint 不取代或复用其支持声明。
- NativeHost 只提供带版本、目标构建和权限声明的 capability。
- 任一 capability 失败、崩溃或 hash 不一致时，自动禁用该项并回退 Runtime/T09。

### Feasibility Boundary

Windows Process Snapshotting 可以捕获目标进程的 VA clone、线程/上下文、句柄和地址空间信息，但官方接口面向捕获、查询和诊断，没有文档化的“恢复整个目标进程”操作。因此：

- PSS 可用于只读诊断、内存布局实验和 checkpoint 原型的证据来源。
- PSS 成功不等于 savestate 恢复成功。
- 同进程恢复仍需处理线程 barrier、上下文、非 cloneable memory、句柄、Mono/Unity native 状态、GPU/音频和外部 IO。
- 跨进程重启后的存档恢复仍必须走 T09。

### In-Scope

- Windows 10/11 x64 用户态 `HollowKnightTAS.NativeHost.exe`。
- 可选、固定导出的 `HollowKnightTAS.NativeBridge.dll`，只为必须在游戏进程内执行的已验证 hook。
- Companion 自动启动/停止 NativeHost；Runtime 发起 capability 请求，用户无需手动运行 exe。
- 三方握手：Runtime session、Companion instance、NativeHost instance。
- 目标 PID/进程映像路径/游戏构建/关键 DLL hash/位数白名单。
- capability discovery、状态、权限、版本、互斥与证据协议。
- 只读进程诊断基线。
- 以下候选 capability 的逐项原型与验证：
  - `native.process.observe.v1`
  - `native.input.override.experimental.v1`
  - `native.clock.trace.experimental.v1`
  - `native.clock.override.experimental.v1`
  - `native.clock.startup.experimental.v1`
  - `native.capture.experimental.v1`
  - `native.checkpoint.experimental.v1`
- NativeHost/Bridge crash、hang、版本不匹配和权限不足的隔离/回退。

### Out-of-Scope

- 内核驱动、管理员权限、系统服务。
- OS 全局 hook、键盘记录、向其他进程注入或扫描其他 PID。
- 远程控制、网络监听、遥测上传。
- 向 movie、脚本或 Studio 暴露任意 `ReadProcessMemory`、`WriteProcessMemory`、地址表达式、DLL 路径或进程启动接口。
- 用 PSS/minidump 文件冒充可恢复 savestate。
- 实现或验证 room-entry 语义关键帧、adapter manifest 与短尾重放；这些属于 T14。
- 保证 GPU、音频设备、Steam、文件/网络连接或未知第三方 Mod 状态可以回滚。
- 把同进程 checkpoint 描述为跨启动存档。

## 2. Architecture

### 2.1 Trust and Launch Chain

```text
Runtime Mod
  ├─ owns HK safe tick + semantic hash
  ├─ requests capability by fixed ID
  └─ never accepts an executable/DLL path from movie
          │
          ▼ authenticated T12 IPC
Companion capability broker
  ├─ verifies native.manifest signature + SHA-256 + RID + protocol
  ├─ starts NativeHost in a kill-on-close Job Object
  └─ brokers session credentials and evidence
          │
          ▼ fixed canonical stdin/stdout + parent-process binding
NativeHost
  ├─ verifies target PID/path/hash/bitness/session
  ├─ exposes only compiled capability IDs
  └─ exports only compiled read-only evidence
```

启动规则：

- Runtime 初始化完成后由 T12 自动启动 Companion。
- 只有设置启用且 Runtime 请求至少一个 capability 时，Companion 才自动启动 NativeHost。
- Experimental capability 默认关闭，必须在游戏内/Companion 设置中显式启用；movie 无权启用。
- 已标为 `verified` 的 capability 也必须匹配精确游戏/Assembly/API/NativeHost/Bridge hash 才能启用。
- NativeHost 使用 `UseShellExecute=false`、固定 manifest entrypoint 和当前用户权限。
- Companion 关闭或失联时 Job Object 终止 NativeHost；不得连带终止 Hollow Knight。

### 2.2 Target Verification

NativeHost attach 前必须核对：

- PID 等于本 session 握手声明的 Hollow Knight PID。
- 进程创建时间与 T01 session 一致，防止 PID reuse。
- 可执行映像 canonical path、SHA-256、PE machine 和版本白名单。
- `Assembly-CSharp.dll`、环境 manifest、Runtime Mod 和 Core assembly hash。
- NativeHost 的父进程必须是签名包内的精确 sibling Companion。
- OS build、架构和能力所需 API。
- Companion/Runtime/NativeHost 协议范围相交。

任何一项不匹配：

- 拒绝 attach/加载 Bridge。
- 写结构化 `target-rejected`，不得退回模糊的进程名匹配。
- Runtime 保持纯 Mod/T09 模式。

### 2.3 Capability State

```text
unavailable
experimental-disabled
experimental-enabled
verified
rejected-build
faulted
unsupported
```

每个 `CapabilityDescriptor` 至少声明：

- ID 和语义版本。
- 是否需要 NativeHost、Bridge、进程读、进程写、线程暂停或图形/音频 API。
- 支持的 OS/架构和完整 build fingerprint。
- 与其他 capability 的互斥关系。
- safe tick/barrier 要求。
- 最大执行时间、内存和磁盘预算。
- 失败回退动作。
- 验收 evidence hash。

### 2.4 Initial Capabilities

#### `native.process.observe.v1`

- 只读采集 module map、thread IDs、PSS capture flags 支持情况和 VA 摘要。
- 不持久化页面内容，不读取用户输入/凭据。
- 目标是建立进程级证据和后续实验边界，不改变游戏状态。

#### `native.input.override.experimental.v1`

- 仅在 T02 无稳定纯 Mod 注入边界时进入实验。
- 输入数据仍来自 T04/T06 的 canonical action frame；NativeHost 不接受 OS 扫描码脚本。
- 必须证明物理输入隔离、按下/释放边沿、焦点切换和异常 cleanup。

#### `native.clock.trace.experimental.v1`

- 第一阶段只观测已知原生时间源调用与线程，不改写返回值。
- 只有 trace 证明具体非确定性来源且 T07 对照需要时，另行启用固定构建 hook。
- 不宣称覆盖未知第三方 DLL 的所有时间源。

#### `native.clock.startup.experimental.v1`

- 只通过固定签名 launcher 创建新的白名单 Hollow Knight 进程，并在 Unity 第一次游戏可见时钟采样前
  安装冻结 Bridge/Payload；不接受任意 PID、路径、DLL、参数或现有进程晚 attach。
- launcher、game、UnityPlayer、Managed、Bridge、Payload、clock profile 和 bootstrap/handoff
  telemetry 全部 hash-bound；任一不匹配终止该新建进程并输出结构化失败。
- 同一 profile 必须同时用于 T24 无 Mod reference、TasPassive/控制面候选和 T09 冷恢复进程。
  只有三者绝对时间与完整 trace 通过独立门禁后才可从 `experimental` 提升为 `verified`。
- 该能力只重建启动环境，不捕获/恢复地址空间，也不写 `UnityEngine.Time`、Hero、FSM、Animator、
  physics 或 RNG；T12 只能以认证 `ColdRestoreIntent-v1` 编排它。

#### `native.capture.experimental.v1`

- Companion/NativeHost 承担编码和磁盘 IO，Runtime 提供带 tick/ledger ID 的帧。
- 帧丢失、重复、音画偏移必须显式记录；捕获不得阻塞 Runtime safe tick。
- 捕获开/关分别做 T07 hash 对照。

#### `native.checkpoint.experimental.v1`

- 这是地址空间/线程/native 状态方向的同进程实验，不是 T14 的版本化语义 DTO 关键帧。
- 只支持同一游戏进程、同一 build fingerprint、同一 session。
- Runtime 先进入 T08 cooperative safe barrier；场景异步加载、存档写入、死亡/重生过渡、未知 native callback 活跃时拒绝。
- Snapshot 必须绑定当前 T05 semantic hash、T03 ledger cursor 和 T06 movie cursor。
- Restore 后立即比对目标 hash，并继续运行至少 600 tick 与无 checkpoint oracle 对照。
- 首次不一致、超时、线程未恢复或外部状态缺口即标记 faulted，停止该 capability 并回退 T09。
- Snapshot 默认只保存在当前 session 临时目录，进程退出即失效；不进入 T09 catalog。

## 3. Protocol and Interfaces

### 3.1 Runtime/Companion Commands

```text
requestCapabilityCatalog
enableCapability
disableCapability
startNativeHost
stopNativeHost
captureNativeEvidence
createNativeCheckpoint
restoreNativeCheckpoint
dropNativeCheckpoint
```

约束：

- `enableCapability`、`createNativeCheckpoint`、`restoreNativeCheckpoint` 只允许来自本地受信 UI/游戏内设置，不能来自 movie command。
- Runtime 最终决定 safe barrier 是否成立。
- NativeHost 最终决定目标进程/权限/build 是否匹配。
- 任一方拒绝即不执行。

### 3.2 Native ABI（v1 未启用）

```cpp
struct HktasBridgeVersion {
    std::uint16_t abi_major;
    std::uint16_t abi_minor;
};

enum class HktasResult : std::uint32_t {
    Ok,
    Unsupported,
    InvalidSession,
    InvalidBuild,
    UnsafePhase,
    Timeout,
    Fault
};

extern "C" HktasResult HktasBridge_Initialize(
    const HktasBridgeInit* init);

extern "C" HktasResult HktasBridge_EnterBarrier(
    const HktasBarrierRequest* request);

extern "C" HktasResult HktasBridge_LeaveBarrier();

extern "C" void HktasBridge_Shutdown();
```

ABI 只包含固定大小 POD、显式长度和版本；不跨边界传 C++ 容器、异常、CLR 对象或未拥有的字符串。

v1 没有 capability 需要进程内 Bridge，所以上述 ABI 是未来启用 Bridge
前必须遵守的门禁，而不是当前发行包已存在的导出。当前 Host 只接受固定
canonical JSON string-map，且直接运行会在读取请求前因父进程不符而拒绝。

```json

```

## 4. Independent Verification

### 4.1 N0 Host and Security Gate

- 正常自动启动、无 capability 时不启动、显式禁用时不启动。
- manifest/签名/hash/RID/协议/目标 PID/创建时间/路径/构建各自篡改。
- 尝试指定第二个 PID、任意 DLL、任意地址或 shell command，全部结构化拒绝。
- 使用标准用户权限运行；若 capability 需要提权则标记 `unsupported`。
- Companion crash 后 NativeHost 在 5 秒内退出，Hollow Knight 保持运行。
- NativeHost crash/hang 后 Runtime 在超时内离开 barrier、恢复输入/time settings 并回退。

### 4.2 N1 Read-Only Observe Gate

- 连续 100 次 attach/detach，不写目标进程。
- PSS flags/API 可用性、module/thread/VA 摘要可重复导出。
- 开启/关闭 observe 跑同一个 T07 oracle，各 10 次，milestone hash 完全一致。
- 工具审计确认没有持久化原始页面内容。

这里的 T07 是与 T12 相同的显式 `DEPENDENCY_ORACLE`：两种 native 设置仍各
执行 10 次真实冷启动正常 run，每个 run 逐一通过 CLI `verification validate`、
证据导入和完整恢复，但不重复运行 T07 自身的 deliberate-divergence 自检。
dependency campaign 在每种模式内及两种模式间只比较有序
`milestoneId/movieTick/semanticSha256` 投影。完整 canonical snapshot、
ledger 与 partial Unity RNG state 继续保留为诊断证据，但在尚无 RNG playback
时不得被提升为 T13 已支持的跨冷启动能力。dependency campaign 不得冒充 T07
独立 `LOCAL_VERIFIED`，T07 默认执行路径仍保留 exact campaign 与 deliberate
divergence。

### 4.3 N2 Capability-Specific Gate

每个 input/clock/capture capability 独立执行：

1. 记录关闭 capability 的 T07 oracle。
2. 只启用一个 capability，至少 10 次独立进程回放。
3. 注入 crash、timeout、disconnect 和版本不匹配。
4. 比较 milestone、ledger、RNG、资源使用和 cleanup。
5. 生成 `verified`、`experimental` 或 `unsupported` 判定。

不得把一个 capability 的 PASS 外推给另一个 capability。

### 4.4 N3 Process-Level Checkpoint Gate

按顺序验证：

1. 静止、安全房间 checkpoint/restore 50 次。
2. Hero 运动、跳跃、冲刺、攻击期间各 20 次。
3. 敌人 AI、粒子、FSM、协程活跃场景各 20 次。
4. 场景加载、死亡、重生、原版存档写入期间必须拒绝。
5. 每次 restore 后立即匹配 T05 hash，并继续 600 tick 匹配无 checkpoint oracle。
6. NativeHost/Bridge 在 capture/restore 各阶段故障注入，Runtime 不得永久冻结。
7. 游戏退出后 native checkpoint 不出现在 T09 catalog；T09 跨启动恢复仍通过。

### 4.5 Startup Attestation Gate

- ClockStartup 必须向当前 Runtime 暴露只读实时状态：run ID、profile、Bridge ABI/status、startup
  hook/latch、deterministic clock、virtual-clock registration、TimeUpdate resume boundary 和 fault 字段。
- Companion 只接受与自身可信 launch evidence 的 PID、创建时间、run ID、profile/hash 全部匹配的
  attestation；命令行或 registration 单独自报不构成 verified。
- reference、产品 source 和 cold target 的角色只进入 evidence，不得改变任何时钟/RNG/scene/input
  行为。baseline/recording 根必须由三者共用同一协议，并在前缀 replay 前完成。
- late injection、普通 Steam 启动、payload 未加载、Bridge fault、run ID/PID/profile 不匹配分别得到
  `StartupUnverified` 或结构化失败，禁止以 bundle 存在或进程 hash 相同替代。

### PASS

- N0 全 PASS，NativeHost/Bridge 只能作用于已认证的当前 HK session。
- `native.process.observe.v1` 通过 N1，且不改变 T07 hash。
- capability 目录准确显示每项的权限、build 和状态。
- 每个标为 `verified` 的 capability 均有独立 N2/N3 evidence；未通过项为 `unsupported` 或默认关闭。
- NativeHost/Bridge 故障不会破坏 Runtime/T09，也不会留下输入锁、时间异常或挂起线程。
- Companion 可按 Runtime 请求自动启动 NativeHost，用户无需手动启动外部 exe。

### FAIL

- 需要管理员权限、内核驱动或 OS 全局 hook 才能工作。
- 可以选择任意 PID、地址、DLL 或命令。
- movie 能启用/执行原生 capability。
- 目标 build 不匹配仍 attach/load。
- PSS capture 成功就被报告为 savestate 支持。
- checkpoint restore 后只比较瞬时 hash，不验证后续 600 tick。
- native checkpoint 被当作跨启动 T09 存档。
- crash/timeout 后游戏永久冻结、输入锁定或必须强杀。
