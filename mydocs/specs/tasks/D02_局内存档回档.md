## 实现边界

使用者在完整帧边界存档；运行中请求应在下一个完整帧边界提交，返回实际目标帧。恢复后的角色、敌人、资源、随机过程和输入游标应属于同一目标状态，能继续正常操作，不能只恢复角色坐标。

当前 baseline + 输入重放方案已能跨进程重建部分目标。继续核对 RuntimeReplayJournal 与 Companion 恢复编排，明确恢复耗时和支持范围；跨进程重建不是瞬时内存快照。若不能覆盖动作中保存、历史编辑或普通局内操作，应补实现，不能用“仅基准点可用”代替要求。

## 独立验收

- 在地面、跳跃/攻击中和战斗中保存，回到各目标后可继续操作；用户存档和其他槽不被污染。
- 定时存档按实际推进帧触发，暂停期间不反复创建；人工与 AI 使用同一入口。
- 回档后重复一段输入，关键位置、生命、敌人阶段与结果稳定，无残留 held 或错位游标。比较的是同一 TAS 的恢复正确性，不要求与另一场原版运行全字段一致。
- 修改过去的输入后，后续重放使用新分支；旧分支仍可选，失效的检查点不能冒充有效。
- 正常退出并重新启动后可以选择保存点恢复；失败可解释、可重试，不伪报 Ready。

保留当前 1331 帧成功恢复作为已有范围证据。后续集中覆盖上述缺口，不重复同一入场恢复或运行 10 轮原版矩阵。

目标快照 v3 已安装，包含 RNG 及当前场景活跃 HealthManager 对象的生命、死亡标志、位置、刚体速度、动画帧及 FSM 状态/数值变量指纹；基线继续 v1，旧格式独立解码，不静默升级。假骑士场景第 932 帧一次保存/恢复通过严格目标校验，Studio 人工单步继续到 933 帧并保持暂停。尚未覆盖无生命组件的投射物、未激活对象及 action 私有计时器，不代表完整场景恢复已验收。当前版本、进程和证据入口见 CURRENT.md。

## 录制起点与同进程读槽

代码定位确认这不是单个按钮限制：

- `ClockController.BeginRecordingClockCalibration/ConfigureRecordingRoot` 只允许首次准备，录制根配置后不可变；重置 Runtime 布尔值无法重新建立时钟根。
- `RuntimeReplayJournal.InvalidateSourceRecordingRootForLoad` 在读槽前后主动撤销已验证的录制根；`OnSavegameLoad/OnAfterSavegameLoad` 随后要求新基线。`IsAvailable` 会因起点失效而关闭。
- `RuntimeCommandDispatcher.LoadExistingGameSlot` 仅允许新进程主菜单首次读槽。当前 movie 命令和输入动作没有描述返回菜单与再次读槽，journal 在非玩法生命周期暂停记录。因此仅移除拒绝条件会丢失重建目标所需的操作。

后续实现沿用首次录制根，记录原生退出到菜单与再次读槽的操作；读槽不得重新播种 RNG、重置时钟或用位置写入代替原生加载。具体事件格式在实现前核对 journal、movie 编辑器和恢复游标，不直接往 v1 帧命令中插入不受支持的命令。

依次完成三个可独立检查的部分：

1. 持久化生命周期记录：为操作记录唯一顺序、提交边界、目标槽及所依赖存档内容的哈希；关联不可变的存档对象，避免回放读取后来已改变的槽。定义等待、完成、失败边界以及事件位于两帧之间时的排序。定向检查序列化、缺失对象拒绝和重复事件拒绝。
2. Runtime 与恢复接线：人工与 AI 提交同一原生操作；完成前阻止并发输入，完成后沿用原录制根及连续游标。冷恢复在对应边界重现操作；异常保留已有分支，不报告 Ready。先完成正常路径，再验证一次退出菜单、同进程读槽、短输入保存及跨启动恢复。
3. 历史编辑接线：编辑影响生命周期事件之前的输入时，相关目标必须重新验证；旧分支和存档内容保留。确认新分支恢复后能继续单步，再与其他交付功能做一次组合检查。

第 1 项的 Core 数据结构已实现于 `ReplayLifecycleLog.cs`：独立 HKLC v1 二进制对象绑定根基线；每条操作绑定输入前缀、前一 movie tick 和从 0 连续递增的序号。同一输入边界按序号执行，原生等待帧数单独记录；Waiting/Failed 只能出现在最后，不能冒充 Completed。读槽记录包含槽号和存档对象 SHA-256，校验器拒绝对象缺失或哈希不符。3 项定向检查通过，包括编解码往返、顺序/未完成约束、损坏数据及对象拒绝。

内容寻址仓库现已提供 `PublishLifecycleLog/LoadLifecycleLog`。发布前复制并验证所引用的槽对象，确认根基线存在且哈希正确；依赖先发布、日志最后发布，复用现有原子对象写入。加载重新检查全部依赖，不将独立日志列为 Ready 存档。2 项仓库检查通过，覆盖重新打开、去重、调用者缓冲区修改隔离、依赖缺失和错误哈希拒绝。

descriptor v2 携带必填的 `lifecycleObjectSha256`，转为手动存档时保留引用；原 v1 默认版本及规范化输出不变。v2 现与 v1 共用环境、基线、目标快照、journal 链及 movie 输入校验，再检查生命周期日志、操作前缀、目标边界和槽对象。槽字节经哈希验证后复制进同一对象集合，不重复读取可变 resolver。缺失或损坏按对应校验返回 Corrupt/JournalGap；完整包仍返回 Incompatible，执行端接通前不生成 Ready package。最新 3 项定向检查通过，包含环境不匹配、目标快照缺失和 journal 缺失拒绝。

前缀校验现已接入 Validator，使用 `MoviePrefixIdentity` 核对操作边界之前的全部输入；边界 tick 计入前缀，-1 表示空前缀。同边界多操作复用一次计算。最新 3 项描述/前缀检查通过，确认过去输入变化被拒绝、未来输入变化可保留关联、缩短 movie 导致边界越界被拒绝。

`ReplayLifecycleCursor` 已实现操作边界领取与完成游标：调用原生操作前领取一次，等待期间不再返回该操作；同边界按序号逐项完成才允许下一帧输入。失败保留活动操作和原因，不自动重试；越过未完成边界会进入失败状态。2 项定向检查通过。原生等待帧数目前仅记录实际值，尚未决定加载等待与 gameplay 帧的 Runtime 调度方式，不能据此声称时钟连续性已验证。

当前尚未接入 Runtime，不是可用的同进程读槽功能。下一步将游标接到帧循环和原生菜单/读槽操作，并实现源端记录。现有 `RuntimeReplayRestoreCoordinator.AdvanceReturnToMenu` 的 DontSave 调用仅服务最初基线恢复，可复用原生调用但不能直接复用其后续基线重置流程。首次启动前已发生且未记录的游戏过程也不能由现有 journal 推导；“任意录制起点”仍需单独证明，不能用同进程读槽成功代替。

Runtime 接线定位已确认：

- `RuntimeReplayJournal.OnSavegameLoad/OnAfterSavegameLoad` 当前无条件进入新基线流程。受控操作必须限定槽、操作序号及活动窗口；只在匹配操作内保留根和 journal，普通未记录读槽继续失效。读槽前后两个钩子不能重复提交操作。源端和恢复端都需要这一处理。
- `RuntimeReplayRestoreCoordinator.RestoreMovieTickGate.TryAuthorizeMovieTick` 是恢复输入的下层门控，当前只识别 PLAYING、场景过渡和暂停状态。需在生命周期活动期间阻止下一 sample；不能只在 `AdvanceReplay` 中检查，否则那时输入可能已提交。
- `RuntimePlaybackController.OnActiveSceneChanged/TryReacquireHeroControlAfterScene` 会在新玩法场景恢复输入资格。新门控必须覆盖这条自动释放路径，直到当前生命周期操作确认完成。
- 原生操作应在完整帧边界发起和完成；操作期间的加载帧不应伪装为输入帧。恢复的目标捕获必须等待目标边界上的全部操作完成，而不能只判断 `currentMovieTick >= target`。journal 的原始 input tick 断档处理可保留，但它本身不能证明加载等待期间的时钟及状态正确。

这些是现代码的接线约束，尚未实现或实机验证。下一次修改应覆盖同一操作从源端领取、原生调用、钩子识别到完成提交的完整路径，不单独开放恢复入口。

源 journal 已加入内部 `BeginLifecycleOperation/CompleteLifecycleOperation/FailLifecycleOperation`。Begin 校验起点、顺序、输入边界及 Waiting 状态；匹配的首次 SavegameLoadHook 和 AfterSavegameLoadHook 保留原根，意外读槽仍失效。原始输入在活动操作期间停记；Complete 核对输入游标未变、读槽钩子和目标状态，再保存内存记录及完成事件。生命周期存在时 IsAvailable 和 FreezeThrough 均关闭普通帧导出，状态明确显示 LifecycleActive 或 LifecycleReplayUnavailable。Runtime 编译通过，无实机验证。

Runtime IPC 的 reloadGameSlot 已调用这些内部方法。Begin 接收 sourceMovie 和槽字节，验证当前 manifest/基线及所有操作前缀，先 Flush 输入，再将 Waiting 日志原子写入当前 journal 的 lifecycle.bin；槽对象存入同目录 lifecycle-objects，按哈希去重，会话预算 64 MiB。读槽钩子再次核对实际 userN.dat 的大小和哈希。Complete 在持久化 Completed 日志后才更新内存游标，失败日志写入不成功时保留原有不可恢复的 Waiting。Runtime 编译通过，磁盘失败和原生加载均未实机验证。

源端调用方已串接完整帧边界、活动序号限定的暂停、原生返回菜单/读槽及超时失败处理。NativeLifecycleInputLease 复用 HeroInputAdapter，在操作期间提交空输入，并在当前 HeroActions 更换后的首次更新前重新绑定；结束或失败到达暂停边界后恢复原绑定。断连先阻止后续原生操作，再等待安全暂停清理。仅编译验证，菜单 UI 干扰及原生加载待实测；公共人工/AI 入口尚未接通。
