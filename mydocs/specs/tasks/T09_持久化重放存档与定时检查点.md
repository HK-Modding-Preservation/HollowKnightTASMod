## 0. Open Questions

- None。本任务中的 `savestate` 明确定义为“baseline + 连续输入日志 + movie cursor + semantic hash”的持久化重放存档，不是进程内存快照。T14 语义关键帧与 T13 同进程进程级 checkpoint 都只能作为可选恢复加速；不得改变本任务的跨启动契约和独立游戏内入口。

## 1. Requirements

### Goal

满足以下用户契约：

1. 使用者可在任意时刻请求保存。
2. 下次启动可列出并选择任意手动或自动存档。
3. Runtime 自动加载对应 baseline、重放前缀并校验目标 hash。
4. 校验成功后停在目标点，movie cursor 指向下一 tick，可从该点继续重放。
5. 支持按有效 movie tick 定时保存。

### “任意时刻”的精确定义

- 用户请求可以在 gameplay、暂停、移动、战斗或 scene transition 期间发出。
- 实际落盘必须对齐 T03 定义的安全 committed tick，不能在物理/FSM 更新到一半时读取状态。
- 存档同时记录 `requestedAt` 与 `effectiveMovieTick`。
- 非安全 phase 的请求排队到下一个安全 tick；UI 必须显示 pending。
- 如果退出前仍未到达安全 tick，请求明确失败，不能伪造成功。

### “定时”的精确定义

- 计时单位为**已推进的 movie tick**，不是墙钟时间。
- 暂停、加载等待或 movie cursor 未推进时，不产生重复自动存档。
- `AutoSaveIntervalMovieTicks` 可配置；默认 `18,000`。
- 自动存档默认保留最近 `20` 个，使用环形淘汰。
- 手动存档永不被自动淘汰。

### In-Scope

- 始终开启的 T06 shadow journal。
- Baseline bundle、content-addressed object store、catalog 和原子事务。
- 手动、定时、movie command 三种创建原因。
- 跨进程选择、恢复进度、hash 验证和继续重放。
- 不依赖 Companion/Studio 的最小游戏内存档目录/恢复入口；T12 只复用同一 API。
- 专用 TAS 槽位保护、覆盖确认、备份与取消。
- Normal replay oracle，以及已经通过 hash 对照的安全快进策略。
- 零个或一个 `IReplayRestoreAccelerator` 的可选集成点；没有 T14/T13 时本任务必须独立通过。

### Out-of-Scope

- 进程地址空间、线程、协程、GPU/音频设备的直接快照；该实验属于 T13，失败时仍回退本任务。
- 原地恢复当前 Unity 对象图。
- room-entry 语义关键帧、状态 adapter 与短尾重放；该加速实现属于 T14。
- 未经确认覆盖普通用户存档槽。
- journal 有 gap 时创建“看似可用”的存档。
- 恢复失败后自动跳到最近似状态。

## 2. Architecture

### 2.1 Why Replay-Based

目标构建的原版 `SaveGameData` 主要包含 `PlayerData` 与 `SceneData`。它不能恢复当前 Hero transform、Rigidbody2D 接触、PlayMaker FSM、协程、对象池和 native Unity 状态。因此：

- 原版存档字节只作为 baseline bundle。
- 任意时刻状态由 baseline 到目标 tick 的连续输入/命令重建。
- 目标 semantic hash 是恢复成功的硬条件。

### 2.2 Always-On Journal

- 新游戏 ready 或 `AfterSavegameLoadHook` 后，先等待原始存档重载锚点满足共同条件：
  `PLAYING`、无场景过渡、movie tick 可推进且
  `Rigidbody2D.velocity=(0,0)`；随后只接受以下两类原版重载状态之一：
  1. `PlayerData.atBench=true` 且 Hero 尚不接收输入的原版坐椅状态；
  2. Hero 可接收输入、`ActorStates.idle`、`onGround=true`，且
     jump/fall/dash/attack/wall-slide 均为 false 的可操控中立状态。
- 满足锚点后使用 `hero-transform-position-v1` 捕获语义状态：位置取稳定的
  `Transform.position`，速度仍取物理事实源 `Rigidbody2D.velocity`；必须连续
  3 个 `LateUpdateEnd` 得到完全相同的 canonical semantic SHA-256，才发布
  baseline。
- 仅“可操控”或仅“连续数帧 hash 相同”都不够：目标构建在加载后会出现持续
  数帧的 `airborne/onGround=false` 瞬态；该状态不可作为可跨冷加载重建的
  raw-save anchor。
- 新 baseline 发布前旧 journal 不得继续提交 input tick；发布后 T06 shadow
  journal 立即开始。
- journal 持续记录 input sample、movie tick、必要命令和 phase mapping。
- 每段写入带 sequence、previous hash 和 segment SHA-256。
- 任意 segment 缺失、乱序或校验失败，将其后的 savepoint 标记为 `JournalGap`，禁止创建/恢复。

### 2.3 Save Transaction

1. 收到 manual/auto/movie-command request。
2. 在下一个 safe tick 固化 journal through target tick。
3. 捕获 T05 semantic snapshot/hash 和 T03 ledger summary。
4. 写入缺失的 content-addressed objects。
5. 在 transaction 目录写 descriptor 和校验清单。
6. flush 文件。
7. 原子发布 entry。
8. 最后原子更新 catalog。

进程在任意步骤退出时，已发布 entry 仍有效；未发布 transaction 下次启动被识别为 incomplete，不进入 catalog。

### 2.4 Restore Flow

恢复策略必须显式区分：

- `FunctionalReplayRestore`：当前同进程返回标题、重新加载 baseline、重放前缀的兼容路径。
  它只能报告 `FunctionalOnly`，可用于存储/编辑器诊断，不能满足 T24 原版逐帧等价回退。
- `VanillaEquivalentColdReplay`：正常产品回退与验收路径。它不写字段，而是由 T12
  Companion 监督关闭当前游戏、按 T13 已验证启动 profile 创建全新进程，再从同一 baseline
  重放。这是 T09/T21/T22 对外宣称“回退成功”的必要路径。

`VanillaEquivalentColdReplay` 固定流程：

1. 选择 replay save，校验 descriptor、objects、manifest、baseline、movie、journal、schema
   及目标 build；选择历史输入分支时同时校验 exact canonical prefix。
2. 在源进程 committed tick 获取专用 TAS slot lease/覆盖确认并封口 journal。当前槽位 bytes
   不同则先创建原字节备份；取消时不得写槽位或创建 restart intent。
3. 创建 canonical `ColdRestoreIntent-v1`，绑定 replaySaveId、baseline/movie/prefix hashes、
   target tick/hash、source session/PID 创建时间、环境 manifest、Runtime/Companion/启动 profile
   hashes 和 parent operation lineage。intent 不包含任意 exe/path/命令。
4. 通过已认证 T12 session 把 intent 原子交给 Companion；Companion 返回单次 claim 后，Runtime
   neutralize input、flush evidence，并正常退出当前进程。Companion 缺失时允许保存为“下次手动
   启动恢复”，但不得把仍在同一进程内的恢复标成等价成功。
5. 新冷进程必须匹配 intent 绑定的全部 hash，并由 Companion 证明是该 intent 创建/关联的精确
   PID。Runtime 只在认证握手后 claim；过期、篡改、重复 claim 或错误环境立即终止恢复。
6. 使用原版 baseline load lifecycle 到达冻结 baseline，再在完整 frame boundary 进入
   `BaselineReady`。用于 T24 的运行必须复用与 reference 相同的 startup clock 和 fixture arming
   合同；不得让 replay 准备额外消费 logical tick。
7. 自动重放 canonical journal/movie prefix `0..target`，显示 operation ID、阶段、tick、百分比和
   预计剩余成本；不得写 Unity 时间、Hero、Animator、FSM、physics、Boss 或 RNG 状态促成收敛。
8. 在目标 tick 捕获未量化 semantic hash，并在 T24 模式继续比较完整 normalized trace（含
   `time.raw/fixedRaw`、phase、input、animation/physics/world/RNG）到场景结束。
9. 所有要求 exact：进入 `Paused`，无 held input，cursor 指向 `target + 1`，intent 原子完成；
   任一首差异进入 `RestoreDesync` 并保留证据，禁止回落 `FunctionalReplayRestore` 冒充成功。
10. 若写入过专用槽位，按策略保留 TAS baseline；普通槽位备份绝不自动删除。崩溃恢复最多把
    intent 标记为失败/待用户处理，不得无界自动重启或重复消费。

T09 自带最小标题界面/游戏内 overlay，用于 list、manual save、auto policy 和 restore；没有 Studio 时也必须满足完整用户契约。

### 2.5 Clock Environment and Original-Semantics Boundary

- 旧版 `unity-capture-delta-equals-fixed-v1` 已退役，不再属于 T09 的支持边界。
  Runtime 不得因 Replay Save/TAS 生命周期写入 `Time.captureDeltaTime`、
  `Time.fixedDeltaTime`、`Time.timeScale`、`Application.targetFrameRate` 或
  `QualitySettings.vSyncCount`；配置项
  `ReplaySaveDeterministicTimingEnabled` 也不得恢复这些写入。
- reference 与 candidate 的确定性验证由同一个外部测试环境提供相同的时钟、
  帧相位和 RNG 条件。该环境必须对两侧对称，不是 Mod 的运行时补丁，也不能作为
  普通用户回放时的隐式状态修改。
- `timeScale` 非 bit-exact `1.0f`、加载或场景过渡期间，journal/movie tick
  fail closed，不得伪造 gameplay tick；原版 hit-stop 与暂停行为原样保留。
- 恢复只能通过干净原版 baseline 重载后重放；目标 canonical semantic SHA-256
  必须完全一致。任何自然 visual/fixed 调度分叉均进入 `RestoreDesync`，不得靠
  改时钟、位置、速度、动画、FSM 或其他 gameplay 状态收敛。

T07 已证明自然 visual/fixed 调度会在移动路线产生分叉，因此 T09 不能仅靠
“相同输入序列”宣称可恢复；相同外部验证条件、干净 load lifecycle 和目标原始
hash 门禁共同构成本任务当前的支持边界。

### 3.3 Catalog and Retention

- Catalog 按 `effectiveMovieTick`、创建时间和 ID 稳定排序。
- 自动淘汰先从 catalog 移除 auto entry，再把 descriptor 移入 store 内部 trash；content object 只有在引用计数核对、事务恢复完成且超过 grace period 后才可回收。
- 手动 entry 不参与自动淘汰。
- 自动 entry 可由用户“固定”为 manual，固定后不再淘汰。
- 手动删除 manual entry 是显式产品操作；由已启用 retention policy 产生的 auto 淘汰和安全 GC 属于本任务授权的后台行为。

## 4. Independent Verification

### 4.1 Offline Storage

- 同内容 objects 去重且 hash 一致。
- catalog/entry canonicalization 重复 100 次字节一致。
- 在事务的每个步骤模拟进程终止；恢复后只有完整 entry 可见。
- corrupt object、缺 segment、错误 manifest、错误 schema 分别得到预期状态。
- 自动 retention 为 3 时创建 5 个 auto，catalog 只保留最新 3 个；manual 全保留。

### 4.2 Manual Arbitrary Save

从同一 baseline 创建至少 5 个手动存档：

1. Hero 静止。
2. 跳跃上升中。
3. 冲刺或攻击中。
4. 战斗中。
5. scene transition 期间发出请求，落到下一安全 tick。

完全退出游戏。下次启动后按非时间顺序选择每个存档，各恢复 10 次。

### 4.3 Automatic Save

- 测试 policy：interval `120` movie ticks，retention `3`。
- 连续推进至少 `1,000` movie ticks。
- 中途暂停足够长墙钟时间，确认不产生重复 auto。
- 至少一次跨场景。
- 重启后选择最早保留、最新和跨场景 auto，各恢复 10 次。

### 4.4 Slot Safety

- baseline slot 未变：无写入直接恢复。
- 专用 TAS slot 已变化：必须等待明确确认。
- 用户取消：slot bytes/hash 完全不变。
- 用户确认：先生成原字节备份，再写 baseline；失败可恢复原字节。

### Historical PASS（已被 T24 部分推翻）

- 每个 manual/auto descriptor 都包含 requested/effective tick 和完整 hashes。
- 5 个手动点与 3 个自动点的跨启动恢复均为 10/10 hash 一致。
- 历史矩阵的 hash 一致曾包含坐椅坐标量化和 TAS 单侧时序 profile，不能作为
  当前 T24 的逐帧等价证明；产物只保留为事务/恢复流程回归证据。
- 成功恢复后处于 Paused，继续操作从 `effectiveMovieTick + 1` 开始，无 off-by-one。
- 暂停期间不重复自动保存；retention 只淘汰 auto。
- transaction crash recovery、corruption detection、slot cancel/backup 全通过。
- 恢复过程不需要使用者手工重放前缀。
- 未注册 accelerator 时全部验收独立通过；accelerator 缺失或失败时自动从干净 baseline 回到同一 full replay 结果。

### Current T24 Re-acceptance

- 未量化的 canonical Semantic Snapshot v1 原始 SHA-256 必须完全一致。
- Runtime 全程不得写 Unity 时钟、Hero pose/control/physics、动画或 FSM 来促成恢复。
- manual/auto/movie checkpoint 均须在独立冷进程中恢复，并通过 T24 的
  phase/input/gameplay/mutation 对照；任一首差异即 fail closed。
- `Time.time/fixedTime` 不属于当前 v1 semantic hash，因此同进程 hash PASS 只能归类为
  `FunctionalOnly`；正式恢复必须由 fresh process 从 tick 0 重建并比较完整 T24 trace。
- `ColdRestoreIntent-v1` 的 source/Companion/new-process lineage、单次 claim、环境 hash、
  slot cleanup 和 crash-loop guard 都是恢复证据的一部分。
- intent 创建前 source、claim 后 target 均须满足 T24 0.80 的实时 startup attestation；target 在相同
  baseline/recording 根完成前不得开始 prefix。未验证的普通启动必须显示 `StartupUnverified`，不得
  回落到 `FunctionalReplayRestore` 冒充正常回退。
- 人工入口与 AI/SDK 入口使用同一存档/恢复实现和同一严格判定。
- source/target movie 必须在源进程退出前写入同一内容寻址对象库。新进程按 intent hash 读取并重新验证
  canonical Movie v1；`seekMovieTick` 和 `applyBranchAndSeek` 不得依赖源进程内存中的 movie。
- seek/branch 使用最近的 exact-prefix replay checkpoint 取得 baseline，但从冷 baseline 直接重放完整目标
  movie 的 `0..target`，不先恢复旧 checkpoint state 再在同进程补短尾。
- replay-save restore 的目标校验模式为 `ExactSavedSemantic`。seek/branch 产生的新状态没有预先存在的可信
  semantic oracle，模式为 `ReconstructedObservation`，只报告 actual hash；不得把 checkpoint 或旧分支
  semantic hash 冒充 expected。T24 的完整逐帧 trace 仍决定该路径能否获得最终等价 PASS。

### FAIL / Downgrade

- shadow journal 在目标点前存在 gap。
- baseline/movie/manifest/schema 不匹配。
- 目标 hash 不一致。
- 普通用户槽位被静默覆盖。
- 恢复只到“附近状态”却标记成功。

失败 entry 保留原始证据并标记具体状态；不得静默删除或改写 expected hash。

## 6. Rollback and Data Safety

- 取消/失败顺序：停止前缀 replay → 输出全释放 input → 恢复 bindings →
  恢复必要的 slot bytes → flush evidence；Runtime 不取得 Unity 时钟写 lease。
- 不自动删除 manual save、普通槽位备份或失败证据。
- 不在仓库、zip 或日志中输出原始存档 bytes。
- 用户若要物理删除 replay save 或备份，必须通过单独、明确操作执行。
