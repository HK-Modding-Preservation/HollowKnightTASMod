## 0. Trigger Evidence

实机已经观察到以下现象：

- 攻击时只出现刀光，Hero 本体没有对应攻击动作，也没有原版攻击反冲；
- 快速二段跳时出现翅膀效果，但 Hero 本体仍留在地面；
- 其他输入驱动的效果、动画、物理和角色状态也可能不同步。

这些现象已经足以判定当前 TAS 路径不满足原版等价。既有 build、单元测试、
input ledger、movie hash、Boss 击杀或 replay 5/5 均不能覆盖这一失败。在本任务
PASS 前暂停 T16 战斗策略调优，任何战斗成功都不能作为有效验收结果。

2026-08-02 的后续实机结果进一步把失败拆成两个独立首因：

- 暂停墙钟期间，纯释放样本曾错误绕过 pause gate；修复为仅允许 vanilla
  scene-transition gate 的释放特例后，逐次单帧 1200/1200 输入零 mismatch；
- 输入修复后，逐次单帧仍只有 141 个 fixed step，而无 TAS 基准有 257 个，
  起椅 tick 从 357 变为 638，攻击/二段跳因此没有进入原版动作路径。

第二项属于时钟环境差异，不能靠补动画、补速度或延长 movie 掩盖。T13 已因本
证据重新打开 `native.clock.override.experimental.v1`；该能力必须同时作用于
无 TAS reference 和 TAS candidate，且两边的 target/vSync/capture delta/fixed
delta 逐 tick 一致，否则 T24 保持 FAIL。

2026-08-08 使用严格相同的沉睡椅子 baseline、统一 50 Hz 外部时钟和完整 input
phase trace 复核后，先前“首个 Right 边沿导致连续模式起椅晚一 tick”的判断不成立：
旧样本没有锁定相同初始化状态，也没有剔除观察器的空闲 phase prelude。稳定 fixture
下连续模式的 514 个可比较 phase event 完全相同，首输入也已经通过 neutral attach
后在目标 `HeroActions.PlayerActionSet.Update` 中提交。

真正能稳定复现本任务现象的是逐次单帧模式：旧候选在 logical tick 101 首次进入
`Double Jump`，而无 Mod reference 已回到 `Airborne`；翅膀、flash、feathers 和
`doubleJumping` 因此多存活一个 Unity frame。根因是 `Time.timeScale=0` 只停止 scaled
time/physics，Unity 仍会在两次外部 `step(1)` 命令之间运行 `Update/LateUpdate`，从而
让 unscaled animation、VFX 和 FSM 在没有对应 gameplay tick 时前进。

修复没有补写 Hero 动画、位置、速度或状态。Companion 驱动的暂停现在只在一个完整
`LateUpdate` 结束后封闭边界，并阻塞 Unity 主线程；命名管道 reader 保持在后台，
收到经过鉴权的 step/resume 命令后在下一次 `FixedUpdate/Update` 之前开启完整一帧。
修复后 tick 101 的 `Airborne`、clip time、翅膀/flash/feathers、jump/double-jump
状态与 reference 的 canonical comparison hash 完全相同。

  调整常数后重试碰运气，也不得使用故障后失控运行产生的 observer 尾部帧作比较证据。
- 下一实现固定为 ABI 4 / profile v7 / provider v3 的显式 TimeUpdate 两阶段恢复：
  `EndMainThreadPause` 只登记 resume request，QPC 在 request 期间继续冻结；外部 payload
  在参考进程和 TAS 进程中对称地向当前 `PlayerLoop` 插入唯一的只读边界 callback，位置
  必须紧邻且位于
  `UnityEngine.PlayerLoop.TimeUpdate.WaitForLastPresentationAndUpdateTime` 之前。
  Unity 2020.2 的该原生阶段负责等待上一帧呈现并更新引擎时间，属于两个 frame 的转换点；
  callback 在此调用新的 native commit，结算暂停区间，然后立即让原版 TimeUpdate 自行
  等待/采样。这样排除人工/AI 命令泵与上一帧尾部墙钟，同时保留原版 presentation wait，
  不伪造 `Time`、Hero、FSM、Animator、Rigidbody、输入或 RNG。
- callback 安装必须 fail closed：当前 loop 中 `PostLateUpdate` 与 `TimeUpdate` 必须各自唯一，
  后者必须含唯一的 `WaitForLastPresentationAndUpdateTime`；二者的线性索引仅作审计，因为
  PlayerLoop 是循环，TimeUpdate 可位于数组首部并在下一 iteration 承接 PostLateUpdate。
  marker 不得重复，且必须能审计其索引、安装次数、调用次数、resume request/commit 次数。拓扑不符、request
  未在下一转换点 commit、重复 request、非主线程调用或下一次 begin 前仍 pending 均立即
  Fault。退出时只移除自己的 marker，不得覆盖其他 Mod 后续安装的 PlayerLoop 结构。

- 设固定步长的精确 Double 值为 `h=(double)(float)0.02`，当前余相归一化为
  `p in [0,h)`，理想 correction 为 `c=h-p`。若 `(float)c` 的误差已经为零，则直接提交；
  若它向上舍入，先提交它的前一个正 Float32；若它向下舍入，先提交该值。第一段因此严格

  二进制格点；上述第二段数值不超过 `2^-29`，因此只需至多 14 个有效二进制位，可被
  Float32 精确表示。第二段提交后必须得到余相 bits exact zero。若理想 correction 本身已经
  可精确表示则只需一段；若非零余相恰为 fixed-step 整数倍，则仍强制先用前一个 Float32，
  避免再次提交完整 `h` 而停滞。
- 实现必须记录每次只读观测到的 residual bits；`DoublePhaseFinalResidualBits` 在成功和所有
  fault 出口均表示最后一次真实观测，不再允许默认零。另导出 downward-quantization count 与
  last correction bits，harness 对 exact zero、非默认遥测和 profile/capability/hash fail closed。

  直至耗尽 128 次后把它解释成偶发启动。

  即可接受与正常 Paused Runtime 相同的非视觉读取、单帧 `step`、多帧 input batch、movie 读取和
  后续输入编辑。交接本身不创建新的 gameplay 对象、不写 Hero/FSM/Animator/Rigidbody/时间/RNG，
  也不惰性启动 replay；只有用户或 AI 后续明确请求输入回放时才创建普通 playback controller。
- 对冷路径，`resumeReplaySaveRestore` 冻结语义为“完成零帧 paused handoff”，不是“让游戏继续跑”。
  Companion 监督器在观察到绑定同一 operation/claim/intent 的 `PausedAtTarget` 后自动发送一次该命令，
  等待 Runtime 发布 `Completed`，随后才释放 kill-on-close 启动租约；普通 `resume` 仍是唯一解除暂停并
  让原版游戏进入下一完整 tick 的命令。
- 外层 `RestoreSettingsLease` 随暂停控制器一起交给统一控制；最终普通 `resume`、断连清理或 Mod
  正常卸载必须在主线程离开当前 guard 前恢复外层与内层设置，并报告 exact restore。若交接前任一
  ownership/模式/cursor/build 绑定不满足，冷恢复必须 `Failed`，不得退回同进程恢复或通过一次
  resume/pause 修补。
- `ColdRestoreOperationState.Completed` 只表示“新进程冷重建、目标验证和 paused handoff 事务完成”；
  harness 的整段 `U[0..end]` 对 `R[0..end]`、suffix、cleanup 与无 held input 门禁仍独立决定 T24 PASS，
  不得因事务完成而缩短逐帧对拍。
- 定向源守卫至少证明：冷 handoff 路径没有调用 `RuntimePauseController.Resume()`；交接后普通
  `step/requestSnapshot/requestMovie/runInputBatch/resume` 走统一控制；同进程
  `FunctionalReplayRestore` 仍保留原来的显式 resume 行为与 `FunctionalOnly` 标签。

## 1. Goal and Non-Negotiable Invariant

对同一个初始游戏状态和同一条逻辑输入时间线：

1. 无 TAS 控制的原版执行；
2. 人工通过 TAS UI 执行；
3. AI 通过 SDK/CLI/MCP 执行；

三者在每一个实际提交给游戏的 gameplay tick 上，必须经过相同的原版输入、
`HeroController`、PlayMaker FSM、Animator、物理、碰撞、敌人和资源更新语义。

允许的差异只有：

- TAS 可在两个完整 gameplay tick 之间暂停墙钟；
- TAS 可请求原版管线完整前进一个或多个 tick；
- TAS 可回退到 replay save，并从相同原版 baseline 重载后重放输入到目标 tick；
- TAS 元数据、IPC、日志、overlay 和观察器自身状态。

不允许为了让 movie 成功而直接修改 gameplay 状态、补播动画、补写速度、强制
FSM 事件、修正位置、恢复控制、重置技能/资源或在 Mod 内改写 RNG。若必须用
外部能力控制时间源、调度或非确定性来源，必须证明无 TAS 基准与 TAS 路径看到
相同的游戏输入和环境值；不能只对 TAS 路径改结果。

## 2. Terms and Comparison Modes

### 2.1 Logical Input Timeline

比较使用 canonical logical input：每个 tick 的方向轴以及 jump、attack、dash、
cast、superDash、dreamNail 等 held/pressed/released 语义。物理键盘、Human UI 和
AI surface 可以有不同传输形式，但提交给原版 `HeroActions` 的值和边沿必须相同。

### 2.2 Authoritative Gameplay Tick

一个可比较 tick 必须覆盖目标构建中原版的一整条更新管线，包括：

- InControl 更新与 `PlayerAction` 状态提交；
- ModHooks/Hero 更新入口与 `HeroController` 原版读取；
- 该 render frame 关联的全部 `FixedUpdate`/2D physics step；
- PlayMaker FSM、Animator 和碰撞/伤害副作用；
- tick 结束后的只读状态采样。

fixture 只能在原版语义条件连续稳定、每个 render frame 恰好一个 fixed
step、Rigidbody 速度为零时宣布 ready。Hero 渲染 Transform 与 Rigidbody
position 是原版管线的两个独立可观察结果，冷启动时可能长期相差 1 ULP；
就绪门禁不得要求二者 bitwise 相等，也不得写 Transform/Rigidbody 强制
对齐。baseline 必须同时保留两套坐标；候选只能匹配无 Mod 冷启动实测目录。

禁止把仅调用其中一部分方法的“伪单步”计为一个 gameplay tick。暂停期间不得
偷偷消费输入边沿、更新 VFX/FSM 或运行部分物理。

`startReplay` 本身不是 gameplay tick，也不得在命令线程/任意 Update 中途制造
可见的首输入边沿。绑定接管必须先处于 neutral；首样本只能在目标 HeroActions
的原版 action-set Update 入口预装。若该 Update 被 pause gate 冻结，则首样本可
保持待提交，但不得观察、推进 cursor 或消耗 step quota。

### 2.3 Required Modes

- `VanillaReference`：不加载 HollowKnightTAS 控制组件，使用确定性的外部物理
  输入播放器；只允许经过审计的被动观察器采样，观察器不得写 gameplay 状态、
  改绑定、改时间或改变脚本执行顺序。
- `TasPassive`：加载发布候选但不开启录制、回放、暂停、观察 overlay 或外部控制；
  同一外部物理输入必须与 `VanillaReference` 等价。这用于证明 Mod 安装本身透明。
- `ManualTas`：Human UI 经统一业务服务提交 canonical 输入和 step。
- `AiTas`：SDK/CLI/MCP 经同一业务服务提交完全相同的 canonical 输入和 step。
- `SequentialStep` 与 `BatchStep`：同一输入逐帧提交及一次提交多帧的结果必须等价。

被动观察器是测试仪器，不属于产品能力。其程序集、hook 列表和 IL/hash 必须进入
证据；若无法证明只读，则该次 `VanillaReference` 无效，不得用 `TasPassive` 冒充
无 TAS 基准。

### 2.4 Fixture Arming Boundary

用于差分验证的影片准备不得消耗 fixture 的 logical movie/trace tick；绝对时间 512 到 768
之间只允许与 Reference 相同的未录制原版空闲帧。候选 harness 的顺序固定为：

1. 使用与 Reference 相同的 startup launcher/v11 bundle 从 suspended process 创建期加载外部时钟，
   到 `Menu_Title` 后保持同一 3 秒墙钟 dwell；不得经 Steam `-applaunch` 或运行中晚注入；
2. 通过同一外部 UI 路径加载冻结测试槽；只读观察器在 absolute time 512 的 semantic-idle 边界写出
   baseline，Candidate 必须先在冻结 no-Mod exact catalog 中找到完整匹配；
3. 在 baseline 之后、absolute time 768 recording arm 之前连接 SDK。Human UI 与 AI SDK 都经统一服务
   获取 lease 并武装 deferred pause；此时 Runtime 仍为 `Running`，但后续无任何 gameplay tick 被计入
   logical movie/trace；
4. 在 unrecorded、未接管输入的区间读取 capability/manifest、生成 canonical movie，完成
   `validateMoviePatch`、`proposeMoviePatch`、`applyMovieBranch`，再武装 deferred `startReplay` 和外部 RNG
   同步。active replay 必须仍为 Idle，movie tick 不得推进；
5. 只在观察器报告 `waiting-for-recording-arm-release` 且上述武装证据完整后释放命名 ManualReset event。
   Runtime 在该目标帧自己的既有 `WaitForEndOfFrame` pause guard 中原子消费 release、启动 replay、完成
   `Paused`；观察器 tick 0 必须来自下一次获准的完整原版 gameplay frame；
6. Sequential/Batch 保持 Paused 并 step；Continuous 显式 `resume` 后运行。Human UI 和 AI SDK 的
   pause/apply/start 必须落到同一 Runtime 状态机和同一 recording-arm gate。

源代码门禁必须证明 fixture load/baseline 排在 deferred pause 之前，deferred pause 排在
validate/propose/apply/deferred start 之前，release 排在全部准备完成之后，且事件只在同一
completed-frame guard 消费一次。实机 phase trace 必须与无 Mod 的 514 个
canonical event 完全相同；即使 gameplay 最终状态相同，多出或缺少任一原版 FSM
事件也保持 FAIL。

## 3. Normalized State Vector

每个 gameplay tick 至少采集以下非视觉字段，并同时保留 raw JSON 与 canonical hash：

### 3.1 Input and Time

- raw physical/transport sample、committed `HeroActions` held/pressed/released；
- input tick、movie tick、scene epoch、render/fixed step count；
- `Time.time`、`fixedTime`、`deltaTime`、`fixedDeltaTime`、`timeScale`；
- 当前 tick 原版方法/phase 顺序及每个 phase 是否实际执行。

### 3.2 Hero Animation and Physics

- transform、facing、`Rigidbody2D` position/velocity/body type/simulated；
- grounded、jumping、doubleJumping、dashing、shadowDashing、attacking、recoiling、
  bouncing、acceptingInput、controlEnabled 等稳定状态；
- 当前 Hero 动画 clip、normalized time/clip frame、Animator speed/enabled；
- nail slash、wings、dash、spell 等衍生对象的 active/transform/lifetime；
- Hero 与地形/敌人的 contact、collision、trigger 和受力结果；
- attack cooldown、recoil/knockback 速度和相关原版 FSM/计时器。

### 3.3 World and Resources

- scene、transition/loading 状态、稳定 PlayMaker FSM active state；
- Hero health/soul/能力可用性；
- 测试敌人的 transform、velocity、HP、damage/death/FSM 状态；
- 可证明影响当前场景的 RNG 状态或外部非确定性输入；
- provider failure、异常、mutation 标志和 held-input 状态。

只比较屏幕像素、只比较最终位置/HP、只比较 movie cursor 或只比较语义总 hash
都不充分。视频只可帮助人工复核，不参与 PASS 判定。

## 4. Equivalence Rules

### 4.1 Exact and Tolerated Fields

- bool、enum、整数、输入边沿、FSM state、animation clip/frame、对象 active、HP/
  soul、事件序列必须完全相同。
- float 默认按 IEEE-754 bitwise 比较。只有先证明差异来自采样序列化而非游戏
  执行时，才可为特定字段登记固定容差；登记项必须包含理由、上限和负对照。
- 已登记的 Hero 渲染 Transform/相对位移和 `timeMinusFixed` 只使用无 Mod
  负对照实测的绝对差上限；ULP 仅保留为诊断，因为它随坐标量级变化。
  这条规则不适用于 `Rigidbody2D` position/velocity，后者仍必须 bitwise exact。
- 用于测量上述渲染噪声的无 Mod cohort 只可在 baseline 签名中排除
  `heroPositionX/Y`；`Rigidbody2D` position/velocity 与其余语义必须仍完全一致。
  同时必须另行保留不排除任何坐标的 exact baseline catalog 及每个成员哈希。
- 同一游戏版本、同一物理输入 trace、同一观察器/采样器与同一外部时钟契约下，
  若已有多批严格首次无 Mod 冷启动矩阵，候选验证使用的 envelope 必须
  先对这些矩阵取并集并重做全部同权威 baseline run-pair 测量；不得
  在候选失败后只挑选上限较宽的单批 envelope。并集矩阵必须记录每个
  源矩阵的绝对路径与 SHA-256，且所有 run 必须再经完整 artifact/hash/
  只读契约校验。任何 TAS 候选 trace 都不得参与 envelope 生成。
- 候选的 Rigidbody X/Y 联合起点若未在无 Mod 目录中整体出现，不得用数值
  容差或“分量各自见过”直接放行。只有当 X 轴的绝对 position 与
  `positionDelta.x` 在全部 tick 上同时 bitwise 匹配一条具有相同 baseline X
  分量的完整无 Mod trace，且 Y 轴以同样规则匹配相同 baseline Y 分量的
  完整无 Mod trace，才可使用轴向 witness 归一化。离散状态、输入相位、
  动画/FSM/资源/Boss 字段仍必须对同一条主参考 trace 逐帧严格比较。
- 派生 Hero render `positionDelta.<axis>` 超出其直接实测包络时，如果 candidate
  的同轴 Rigidbody 与主参考不同，只能复用上一条已经对整条 trace 预验证通过的
  单一同轴 witness；不得只检查当前帧，不得为不同 tick 选择不同 witness。即使
  witness 通过，当前 render position、tick-0 render 原点和 Float32 派生关系仍须
  独立满足冻结包络与逐位重算条件。
- 外部主机在就绪后通过 ManualReset 的共享“输入开始”锁存器激活两侧观察器的
  命名输入帧 handshake；禁止在锁存器置位前预装的物理键触发 capture，也禁止依赖
  两个 Unity `Update` 的未定脚本顺序转发 RNG reset。观察器的
  `DefaultExecutionOrder(-32000)` runner 只能在受控 frame-zero 边界发出独立 RNG
  request；外部验证 payload 在两侧相同的下一次
  `HeroActions.PlayerActionSet.Update` 输入边界只调用一次
  `UnityEngine.Random.InitState`，并必须在任何后续执行前立即读回四个真实 origin
  word 再 ack。观察器未取得该 snapshot 时不得开始 gameplay capture。运行中的
  Unity 全局 RNG current state 只能在独立无 Mod 负对照证明粒子/渲染壁钟调用会
  改变其相位后标记为不参与 gameplay hash 的诊断字段；这不得放宽同步 origin、
  Hero、FSM、物理、碰撞、资源或 Boss 字段。
- 墙钟、进程 ID、日志时间、IPC latency、TAS UI/metadata 从 gameplay hash 中排除。
- 暂停墙钟不对应 gameplay tick；恢复后的下一个 tick 必须与基准同序号 tick 对齐。

### 4.2 First-Difference Discipline

一旦任一字段首次不同，立即冻结并生成：

- 前后至少 8 个 tick 的 normalized state；
- 输入提交、Update/FixedUpdate/FSM/Animator phase trace；
- 相关对象与字段的 before/after；
- 调用栈或目标方法 patch/hook 清单；
- 分类：input phase、partial step、time、physics、animation、FSM、mutation、RNG、
  observer contamination 或未知。

不得通过增加攻击脚本容错、延长躲避、强制动画或直接写状态掩盖首差异。

## 5. Forbidden Runtime Mutations

正常录制、回放、人工 TAS、AI TAS、暂停、步进和 scored run 中，运行时不得：

- 写 Hero/敌人 transform、velocity、`cState`、Animator state 或 PlayMaker variable；
- 调用 `RegainControl`、强制 animation/FSM event、补发碰撞/伤害或生成攻击对象；
- 写 health、soul、能力 cooldown、Boss HP、完成标志或场景选择；
- 在 Mod 内调用 `UnityEngine.Random.InitState` 或改 RNG state 来让重放一致；
- 在一个 tick 内只运行输入/VFX 而跳过 Hero/Animator/physics，或反之；
- 通过反射/IL hook 改原版分支结果、更新顺序、delta time 或 fixed-step 数量。

T15 debug-only typed mutation 可继续存在于隔离调试进程，但必须：

- 与普通 TAS capability、lease 和 UI 主流程显式隔离；
- 第一次成功立即永久标记 `NonVerifiableDebugMutation`；
- T24/T07/T16 evidence 启动与完成均 fail closed；
- 不得作为任何等价性测试的准备步骤或恢复手段。

### 6.1 机器可读场景契约

上述“逐帧等价”和“目标机制确实发生”是两道独立门禁。即使无 Mod
和候选轨迹完全相同，只要影片没有真正触发指定攻击、二段跳、受伤或 Boss
状态，本场景仍必须 FAIL。每个场景使用独立 JSON 契约，至少冻结：

- `scenarioId`、`schemaVersion`、起始存档槽与起始场景；
- movie 相对路径、SHA-256、展开 tick 数与数字输入 action mask；
- 每帧必须存在的可比较字段列表；
- 目标动作的 coverage assertion，及其最小触发次数；
- 允许的终止场景/状态和超时上限；
- 要求执行的表面与调度模式。

契约验证器必须 fail closed：拒绝未知字段、未知 assertion type、重复
assertion id、movie/hash/tick 不一致、轨迹不连续、必需字段缺失或未达到最小观测次数。
每个 assertion 的结果必须记录命中 tick、命中数、首个失败 tick 和实际值。

第一版验证器只接受以下冻结 assertion type：

1. `seen`：至少 N 帧满足单字段类型化比较；
2. `coincident`：至少 N 帧同时满足多个条件；
3. `transition`：指定字段按顺序出现 from/to；
4. `delta`：同一字段在轨迹中至少上升或下降指定量；
5. `ordered-match`：单字段按顺序命中一组完整锚定的正则；
6. `all-when`：触发条件命中至少 N 帧，且每个命中帧都必须满足全部关联条件。

字段条件只允许 `eq`、`ne`、`gt`、`ge`、`lt`、`le`、`regex`、
`in`；bool/int/long/float/string 必须按轨迹的 `kind` 解析，不得将字符串
隐式转换成数值。

## 11. Rollback

- 修复只允许减少 TAS 对原版运行的干预；不加入补动画、补速度或脚本容错。
- 若现有 Mod 内确定性/RNG/控制恢复功能违反本 Spec，先从正常 TAS/scored capability
  禁用并保留为显式实验，直到有外部等价实现和独立证据。
- 若无法实现完整 tick step，则产品降级为录制/整段回放/只读 Inspector；不得继续
  宣称帧级 TAS 或完成 T16。
