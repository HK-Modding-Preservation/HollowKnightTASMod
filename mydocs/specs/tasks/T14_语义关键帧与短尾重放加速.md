# Task Spec T14: 语义关键帧与短尾重放加速

- **Status**: DOWNGRADED_REPLAY_ONLY_VERIFIED
- **Gate**: G3A Optional Restore Acceleration
- **Depends On**: T09, T10
- **Produces**: 版本化房间入口关键帧、适配器 manifest、T09 恢复加速索引、短尾重放恢复与自动回退报告

## 0. Open Questions

- None。v1 只承诺 `ReplayOnly` 与经过实机白名单验证的 `RoomEntry` 支持层级；任意运行中对象/FSM 的原地快照属于后续 `RegisteredRuntime` 扩展，不阻塞本任务。

## 1. Requirements

### Goal

在不削弱 T09 跨启动契约的前提下，减少长路线存档恢复时需要重放的 tick 数：

1. T09 仍可在任意时刻创建手动或定时存档。
2. T14 只在已验证的稳定边界捕获语义关键帧 `K`。
3. 目标存档 `T` 关联最近的兼容关键帧 `K <= T`，恢复时应用 `K` 后只重放 `(K, T]` 的 journal 尾段。
4. 到达 `T` 后必须命中与 T09 相同的 T05 semantic hash，并停在 `T + 1` cursor。
5. 关键帧不可用、损坏、不兼容或恢复失步时，自动丢弃加速路径并回退 T09 从 baseline 完整重放。

### Non-Negotiable Contract

- **T09 是唯一持久化真相源**：T14 可以加速 T09，但不能让 T09 依赖关键帧才能恢复。
- **任意存档点不等于任意快照点**：用户在 tick `T` 保存时，只固化精确的 T09 descriptor；T14 不在未知运行状态强行捕获对象图。
- **正确性先于速度**：关键帧恢复必须与 T09 full replay 在目标 hash 和后续 oracle 上完全一致。
- **失败必须可见且可回退**：不允许修改 expected hash、跳到附近 tick、静默忽略缺失适配器或继续使用部分应用的关键帧。
- **普通游戏存档安全不变**：关键帧不得覆盖普通用户槽位；加载仍使用 T09 的专用 TAS slot lease 和原版生命周期。

### Terminology and Tick Semantics

- `B`：T09 baseline bundle。
- `J(a,b]`：从 committed tick `a` 之后到 `b`（含 `b`）的连续 T06 journal。
- `K@k`：在 committed tick `k` 捕获的语义关键帧。
- `T@t`：目标 T09 replay save，`effectiveMovieTick = t`。
- `FullReplay(B,T)`：T09 从 baseline 重放到 `t`。
- `AcceleratedReplay(K,T)`：恢复 `K@k`，再重放 `J(k,t]`。

成功条件：

```text
Hash(FullReplay(B,T), t)
  == Hash(AcceleratedReplay(K,T), t)
  == T.ExpectedSemanticHash
```

恢复成功后的下一输入 cursor 必须始终为 `t + 1`。当 `k == t` 时尾段为空，但仍必须执行目标 hash 校验。

### In-Scope

- `semantic-keyframe-v1` descriptor、schema、content-addressed artifacts 和兼容性校验。
- `keyframe-adapter-manifest-v1` 与显式适配器注册表。
- `ReplayOnly`、`RoomEntry`、`RegisteredRuntime` 支持层级的数据模型；v1 产品验收只要求前两层。
- 房间入口、Hero ready、T03 safe committed tick 上的关键帧 eligibility probe。
- `PlayerData`、`SceneData`、Hero、RNG 和 tick/input cursor 的白名单适配器。
- 通过游戏正常 save/load/scene lifecycle 重建对象，再按确定顺序应用允许的语义状态。
- T09 `IReplayRestoreAccelerator` 可选集成点。
- 关键帧共享、引用计数、原子发布、兼容性失效和安全回收。
- full replay 与 keyframe + tail 的 10-run 一致性、后续 600 tick oracle 和回退验证。
- 加速效果的 tick 数与墙钟耗时报告；未取得数据前不承诺固定倍数。

### Out-of-Scope

- 通用反射深拷贝全部 `GameObject`、`MonoBehaviour`、PlayMaker FSM 或整个托管堆。
- 序列化/恢复 `UnityEngine.Object` 引用、delegate、协程/iterator、native pointer、物理 contact、GPU/音频设备状态。
- 在任意动画、攻击、碰撞、死亡、过场、加载或原版存档写入中点捕获 v1 关键帧。
- 未登记的敌人、对象池、动态 prefab、第三方 Mod 状态和未知静态字段。
- 同进程内存克隆、线程/寄存器/句柄快照；这些属于 T13。
- 用关键帧替代 T09 baseline、journal、目标 semantic hash 或跨启动目录。
- 将同进程 Celeste-style 内存缓存作为 v1 持久化契约。

## 2. Architecture

### 2.1 Source-of-Truth Boundary

创建 T09 存档时：

1. T09 先独立完成 descriptor、journal head 和 target hash 的原子提交。
2. T14 查询最近的兼容 `K@k`，其中 `k <= t`。
3. 找到时只在独立 accelerator index 记录 `replaySaveId -> keyframeId`；不得改写 T09 descriptor。找不到时 entry 仍为 `Ready`。
4. 删除或失效关键帧不能让 T09 entry 变为损坏。

恢复规划必须先通过 T09 validator，再尝试 T14：

```text
Validate T09
  ├─ FAIL -> T09 的 Corrupt/Incompatible/JournalGap
  └─ PASS -> TryPlanAcceleratedRestore
               ├─ unavailable/incompatible -> FullReplay(B,T)
               └─ candidate K -> TryRestore(K) -> Replay J(k,t]
                                      ├─ hash/oracle PASS -> success
                                      └─ any fault -> clean reset -> FullReplay(B,T)
```

若关键帧已经部分应用，回退前必须退出当前 restore attempt、释放输入/时间 lease，并重新走一次干净的 baseline load；禁止在已污染对象图上直接继续 full replay。

### 2.2 Capture Eligibility

v1 关键帧只有同时满足以下条件才允许捕获：

- 当前为 T03 定义的 committed safe tick。
- scene load 已完成，`HeroController` 已 ready，Hero 可稳定读取。
- 当前位于白名单 room-entry gate，且该 gate 已通过重复实机验证。
- 没有 scene transition、死亡/重生、原版存档写入、过场或菜单切换。
- 没有已知 coroutine/native callback/异步加载临界区。
- T06 journal 连续，T05 snapshot 可生成，T10 RNG 状态处于受支持 profile。
- 游戏构建、关键 DLL、Mod manifest、设置、baseline 与 adapter manifest 均有稳定 hash。
- 所有 required adapter 的 `CanCapture` 均返回 `Eligible`。

任一条件不满足时返回结构化原因；不得阻塞游戏等待“变得安全”，也不得捕获半成品关键帧。

### 2.3 Support Tiers

| Tier | 含义 | v1 行为 |
|---|---|---|
| `ReplayOnly` | 当前路线/环境没有安全关键帧 | 完整使用 T09 baseline replay。 |
| `RoomEntry` | 在已验证房间入口保存持久状态和最小运行态 | 先恢复入口，再重放当前房间内的短尾。 |
| `RegisteredRuntime` | 显式登记对象/FSM/实体适配器 | 仅保留协议位置；后续逐对象 Spec 和实机证据通过后启用。 |

未登记第三方 Mod 存在时默认降为 `ReplayOnly`。第三方 Mod 只有提供版本化 adapter、声明 required/optional、绑定精确 manifest 并通过同等 oracle，才能进入更高 tier。

### 2.4 Adapter Boundary

每个 adapter：

- 有稳定 `adapterId`、schema version、payload hash、required/optional 标记和精确 build/profile 范围。
- 只能访问编译期允许的 HK 语义字段，不接受 movie 提供的类型名、成员名或反射路径。
- Capture/Restore 都在 Runtime 主线程的规定 phase 执行，并有预算和结构化结果。
- Restore 必须幂等或明确拒绝第二次应用。
- 不得持久化原始 Unity instance ID 作为跨启动身份。

payload 只能包含标量、枚举、稳定字符串 ID、排序集合和版本化 DTO。任何 `UnityEngine.Object`、delegate、iterator、native handle 或任意类型反射图在 schema/运行时双重拒绝。

### 2.5 Capture Flow

1. `KeyframeEligibilityProbe` 在候选 room-entry gate 评估条件。
2. 捕获 T05 canonical semantic snapshot、T10 RNG 状态、T03 tick stamp 和 T06 journal head。
3. 按稳定 `adapterId` 顺序执行 adapter capture。
4. 对每个 canonical payload 计算 SHA-256，生成 adapter envelope。
5. 生成 descriptor，并验证所有 required envelope 完整。
6. 事务目录写入、flush、原子发布 content objects 和 descriptor。
7. 最后更新 keyframe index；失败事务下次启动只作为 incomplete evidence，不可供恢复使用。

### 2.6 Restore Flow and Apply Order

1. T09 validator 验证目标存档、baseline、journal、manifest 和 target hash。
2. 选择最近的兼容 `RoomEntry` 关键帧；验证 descriptor、全部 object hash、adapter manifest 与 `k <= t`。
3. 取得 T09 专用 TAS slot lease，安装关键帧绑定的持久化 `PlayerData/SceneData` bundle。
4. 通过原版 load 与 scene-entry lifecycle 先还原 `PlayerData/SceneData` 并进入关键帧目标场景。
5. 进入 T08 cooperative pause，确认 Hero ready 和 scene epoch。
6. 对原版生命周期未覆盖的运行态按下列顺序恢复：
   1. 校验 scene load/entry lifecycle 产生的稳定对象；
   2. `RegisteredRuntime` 对象/FSM（v1 不启用）；
   3. Hero transform、velocity 与白名单状态；
   4. T10 RNG 与全局确定性状态；
   5. input held state、tick ledger 与 journal cursor。
7. 在关键帧 tick `k` 立即计算 T05 hash；不一致则终止加速并干净回退。
8. 重放 `J(k,t]`。
9. 在 `t` 比对 T09 expected hash；一致后进入 Paused，cursor 为 `t + 1`。

### 2.7 Compatibility and Fallback

下列任一情况使 candidate 变为 `Incompatible` 或 `FallbackToReplay`：

- 游戏、Assembly、API、Mod、设置、baseline、journal chain 或 adapter manifest hash 不匹配。
- required adapter 缺失、版本不支持、payload 损坏或 apply 超时。
- 目标 scene/gate/epoch 不匹配。
- 关键帧 hash、目标 hash或后续 oracle 首次不一致。
- 捕获时 eligibility 证据缺失。
- 未登记第三方 Mod 或未知运行态被检测到。

回退结果必须记录 candidate ID、失败 adapter/phase、expected/actual hash、是否发生部分应用、cleanup 结果和最终 T09 恢复结果。只有 T09 最终 hash 一致，用户界面才显示恢复成功。

### 2.8 Storage and Retention

- 多个 T09 savepoint 可以共享同一个关键帧及 payload objects。
- keyframe descriptor 与独立 accelerator index 都要原子发布；index 可删除、可重建，不属于 T09 descriptor 的完整性条件。
- 删除关键帧只移除 accelerator；不得删除仍被 T09 baseline/journal/savepoint 引用的 object。
- 自动 GC 只有在引用图核对、事务恢复完成和 grace period 到期后运行。
- 无关键帧、关键帧全部失效或用户关闭加速时，T09 行为与输出必须完全不变。

### 2.9 Celeste Reference Boundary

CelesteTAS 的 `SavestateManager` 在静态列表中保存 TAS controller clone、checksum 和 slot，并调用 Speedrun Tool 的 save/load；核心 savestate 是同进程内存态，不是跨启动存档。Speedrun Tool 的 `StateManager` 深拷贝 `Level`、`SaveData` 和 transition iterator，再把克隆状态恢复进 live `Level`；`SaveLoadAction` 还显式处理静态状态、RNG、输入、音频和其他 Mod。其 `DeepClonerUtils` 对图形资源、Scene、FMOD、弱引用和 `DynamicData` 做特殊规则，`DesyncRiskAnalyzer` 会拒绝 Lua/过场等不安全状态。

本任务借鉴的是：

- eligibility gate；
- 显式 adapter registry；
- RNG/input/static state 的独立恢复动作；
- 恢复后 hash/oracle 验证。

本任务不照搬：

- 对 HK 全对象图做通用 deep clone；
- 把同进程内存引用直接持久化到磁盘；
- 假定 Celeste 的 `Level` 聚合边界也存在于 HK；
- 把 Celeste 同进程恢复成功外推成 HK 跨启动能力。

## 4. Independent Verification

### 4.1 Offline Schema and Store

- canonical descriptor、adapter manifest 和 payload 重复 100 次字节/hash 一致。
- unknown field、unknown required adapter、重复 adapter ID、乱序、错误 schema/hash 全部 fail closed。
- 在事务每一步模拟退出；只有完整发布的 keyframe 可进入 index。
- 多个 savepoint 共享一个 keyframe；删除一个引用不回收仍被引用的 object。
- 在完全不注册 accelerator 时，T09 全部现有测试仍通过。

### 4.2 Room-Entry Parity

至少选择 3 个白名单房间/路线，每条路线从同一 baseline 建立 `RoomEntry` 关键帧，并创建 5 个目标 savepoint：

1. Hero 静止。
2. 跳跃上升中。
3. 冲刺或攻击中。
4. 战斗中。
5. scene transition 请求发出后落到安全 committed tick。

对每个目标分别执行：

- T09 full replay 10 次；
- T14 keyframe + tail 10 次；
- 比较目标 T05 hash、ledger cursor、RNG 计数和下一 tick input state；
- 从目标点继续至少 600 tick，与无关键帧 T07 oracle 比较全部 milestone。

### 4.3 Fallback Matrix

逐项注入：

- keyframe object 损坏或缺失；
- adapter manifest 改动；
- required adapter 缺失/版本错误/超时/抛异常；
- 游戏/Mod/设置/baseline/journal hash 不匹配；
- 捕获发生在 transition、死亡、保存写入或未知 Mod profile；
- 关键帧即时 hash 或目标 hash 不一致。

每种情况都必须：

1. 报告精确失败原因。
2. 清理部分恢复产生的 lease/输入/时间状态。
3. 从干净 baseline 自动回退 T09。
4. T09 最终恢复 10/10 hash 一致。

### 4.4 Acceleration Evidence

每条代表性长路线同时记录：

- full replay tick 数、加载次数、墙钟耗时；
- keyframe restore 固定成本、tail tick 数、加载次数、墙钟耗时；
- P50/P95 和环境 manifest；
- 捕获/存储体积、关键帧共享率和 fallback 次数。

PASS 不要求预设倍数，但至少一条代表性长路线必须证明 tail tick 数小于 full replay；若墙钟未改善，功能仍不得宣传为“更快”，只保留实验数据。

### PASS

- T09 在没有 T14 artifacts/accelerator 时独立通过全部契约。
- 3 个房间、5 类目标点的 full replay 与 keyframe + tail 均各 10/10 目标 hash 一致。
- 每次成功恢复后 cursor 为 `t + 1`，且后续 600 tick 命中 T07 oracle。
- 所有不兼容、损坏、缺 adapter 和 unsafe capture 场景都自动回退 T09，且不覆盖普通槽位。
- 未登记第三方 Mod 只使 tier 降为 `ReplayOnly`，不破坏 T09。
- 关键帧存储、共享、事务恢复和 GC 验证通过。
- 加速报告如实给出 tick/墙钟数据，不作未验证性能承诺。

### FAIL / Downgrade

- T09 restore 依赖关键帧才能成功。
- 在任意运行中状态通用反射/深拷贝对象图。
- manifest/adapter 不匹配仍应用 payload。
- 关键帧或目标 hash 不一致后继续恢复或改写 expected hash。
- 部分应用失败后不干净重载 baseline 就继续 full replay。
- 只验证恢复瞬间，不验证后续 600 tick。
- 将同进程缓存或 T13 native checkpoint 当作本任务的跨启动保证。

失败时禁用对应 gate/adapter/关键帧或全局 T14 accelerator；T09 保持 `Ready`。原始失败证据不得静默删除。

## 6. Rollback and Data Safety

- `EnableSemanticKeyframes=false` 时不捕获、不规划、不应用关键帧，T09 原流程保持不变。
- 删除 keyframe index/descriptor 只会失去加速；T09 replay save 仍可从 baseline 恢复。
- 部分 restore fault 时：全释放 input → 恢复 time/binding lease → 卸载污染 session → 重新安装 T09 baseline bytes → 走正常 load lifecycle → T09 full replay。
- 不自动删除手动 T09 存档、普通槽位备份或失败证据。
- schema/adapter 升级默认使旧关键帧 `Incompatible`，不得就地猜测迁移；迁移器必须另有 canonical test vectors。
