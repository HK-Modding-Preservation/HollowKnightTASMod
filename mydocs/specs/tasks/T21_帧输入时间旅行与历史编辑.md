# Task Spec T21: 帧输入、时间旅行与历史编辑

- **Status**: READY_FOR_IMPLEMENTATION
- **Gate**: G6 Product Completion
- **Depends On**: T04, T06, T09, T14, T15
- **Produces**: libTAS 式基础创作能力的统一控制内核

## 1. Goal

为人类和外部 AI 提供同一套 TAS 创作原语：单帧输入、单帧步进、多帧输入、
创建存档、回退到任意存档点、修改过去的输入并从分叉点重新执行。所有原语都以
input tick 为坐标、非视觉、可审计、可撤销，并最终生成 T04 canonical movie。

这里的 `savestate` 默认是 T09 的持久化语义检查点加确定性重放。若当前构建没有
完整进程快照，能力目录必须明确报告 `ReplayCheckpoint` 及预计恢复策略/成本，不能
把它标成 libTAS 式即时 RAM snapshot；功能上仍必须支持保存、列出、选择和向后恢复。

## 2. Canonical Operations

### 2.1 `stepWithInput`

原子完成：

1. 在 Paused safe point 校验 lease、`expectedMovieTick`、`expectedSceneEpoch` 和
   当前 state hash；
2. 设置恰好下一个 input tick 的 `held/axis`；
3. 前进一步到 `InControlCommittedTick`；
4. 自动提交 release/下一中立边沿所需状态，但不额外推进 movie tick；
5. 返回实际 input sample、前后 tick/stamp/hash、Hero/Boss 最新结构化状态。

失败不得消费 tick。重复 idempotency key 返回同一结果，不重复输入。

### 2.2 多帧输入事务

提供 `beginInputBatch`、`appendInputBatch`、`commitInputBatch`、`cancelInputBatch`
或语义等价 API：

- 使用 T04 `frames` 语义和动作顺序；
- 单个 IPC payload 可以有安全上限，但客户端可分块提交任意长度，整体遵守 T04
  最大 expanded ticks；
- commit 前不影响游戏；commit 后按 pause/step/run-until 门禁消费；
- transaction hash、每块 hash、expanded ticks 和最终 journal 范围可核对；
- 断线、lease 过期、scene epoch 意外改变时取消未消费部分并 neutralize input。
- 当前实现固定使用上述四个命令 ID；事务绑定 client、connection、lease、起始
  movie tick 与 scene epoch，每块要求从 0 开始严格连续，整体最多
  `10,000,000` input ticks。commit 前只保存在 Companion 内存，不上传 Runtime。

### 2.3 存档与回退

复用并补齐 T09/T15：

- `createReplaySave(label, movieTick)`；
- `listReplaySaves` 返回 tick、baseline、movie ID、父 lineage、恢复策略、预计成本、
  pin/automatic 和完整性状态；
- `restoreReplaySave(id)` 可选择任意已有检查点，不只最新检查点；
- `seekMovieTick(target)` 自动选取不晚于 target 的最近兼容检查点，再确定性重放短尾；
- 正常 `restoreReplaySave/seekMovieTick` 必须创建 T09 `VanillaEquivalentColdReplay` operation；
  调用返回可跨进程继续查询/订阅的 operation ID，而不是假设一次 IPC 连接内同步完成；
- 新游戏进程复用同一 operation/lease owner identity 重新认证，完成后必须 Paused、无 held input，
  返回精确 target tick、source/Companion/new-session lineage 和完整等价性报告；
- 现有同进程路径只能经显式诊断命令请求并报告 `FunctionalReplayRestore/FunctionalOnly`，
  UI、SDK、CLI、MCP 均不得把它显示为正常回退成功；
- 存档、回退、覆盖确认、取消和失败恢复都可由 UI/API 等价执行。

### 2.4 修改过去输入

提供 typed timeline edit：

```text
replaceInputRange(startTick, deleteCount, replacement)
insertInputRange(startTick, frames)
deleteInputRange(startTick, count)
```

- 基于 exact base movie ID 的 content-addressed branch；
- 先 parse/validate/canonicalize，不直接覆盖当前 branch；
- 返回旧/新范围、tick delta、branch movie ID、diff 摘要和受影响的检查点；
- `applyBranchAndSeek(branchId, targetTick)` 原子应用 branch，选择分叉点之前最近的兼容
  save，创建 cold-restore operation，在全新进程中从同一 baseline 重演完整 prefix 到 target；
- 保留 undo/redo 所需 parent lineage，修改过去不能破坏原 movie 或 save；
- 编辑导致旧检查点 movie prefix 不匹配时显式失效，不静默复用。
- 检查点兼容性比较 canonical 前缀的前 `effectiveMovieTick + 1` 个已提交输入及
  其内部事件；锚定在 tick `N` 的事件发生在第 `N + 1` 个输入之前，因此当存档
  最后提交 tick 为 `N - 1` 时，该边界事件不属于存档前缀。
- `seekMovieTick` 与 `applyBranchAndSeek` 通过 `movieSeekProgress` 报告
  `PreparingIntent -> AwaitingSourceExit -> ColdLaunching -> AwaitingNewSession -> BaselineReady ->
  ReplayingPrefix -> PausedAtTarget -> Completed/Failed`；成功后必须由统一控制器保持 Paused，
  且 authoritative movie tick 精确等于 target。旧进程断开不是失败，operation 状态由 Companion
  持久化并由新连接续订；过期/篡改/重复 claim 或错误 build/phase 立即终态失败。

## 3. Shared State Machine

允许状态：`Idle`、`Paused`、`SingleStepPending`、`BatchStaged`、`BatchRunning`、
`PreparingIntent`、`AwaitingSourceExit`、`ColdLaunching`、`AwaitingNewSession`、`BaselineReady`、
`ReplayingPrefix`、`PausedAtTarget`、`Faulted`。任何时刻只有一个写操作所有者。

- 所有写操作要求 ApprovedControl + exclusive lease；
- 所有写操作带 expected mode/tick/epoch；
- scene load 使用 T19 gate；
- restore/seek/edit/replay 与 debug mutation 互斥；
- disconnect/stop/fault 统一走 neutral input、time/GC/binding restore。

## 4. Verification

1. 从暂停状态分别提交 left、right、jump、attack 的单帧输入，逐 tick 对照实际
   `InputSample` 与 Hero 状态；失败请求不推进。
2. 分块提交至少 10,000 ticks，多帧执行结果与同内容 T04 movie 的 input ledger
   逐 tick 相同。
3. 在 ticks A/B/C 创建三个存档，按 C→A→B→A 任意顺序各经全新进程恢复；每次精确到
   目标 tick，完整 trace 与未回退分支相等，存档文件和原用户槽 hash 不变。
4. 把已经执行过的 `[start,end)` 输入替换后，自动回到 start 前检查点并重演；证明
   新分支结果变化、旧分支仍可恢复。
5. 覆盖 stale tick、错误 epoch、无 lease、ReadOnly、断线、恢复取消、损坏存档、
   不兼容 prefix 和重复 idempotency 的负测试。
6. 最终 `.hktas` canonical，记录与执行 input ledger 一致。

## 5. PASS

- 列出的六项创作能力全部可用：单帧输入、步进、存档、回退、多帧输入、修改过去
  输入；
- 功能可组合成 observe/edit/rewind/replay 循环；
- UI、SDK、CLI、MCP 均通过 T22 的同一内核访问，不存在 AI 子集；
- 所有失败都 fail closed，且无输入、时间、存档或 branch 污染。
- 正常回退均有跨进程 lineage 和 T24 全字段等价证据；`FunctionalOnly` 不计入能力 PASS。

## 6. FAIL

- 单帧输入只能靠物理键盘；
- AI 只能整段上传 movie，不能控制下一帧；
- 只能恢复最新 save，不能选择任意存档点；
- 修改历史必须手工改文件并从头重启，缺少分支/seek；
- UI 有隐藏能力而 API 不可用，或 API 绕过 UI 使用的安全校验；
- 把 replay checkpoint 宣称为完整进程快照。

## 7. Rollback

输入事务和 timeline branch 均为 content-addressed 临时对象；未 apply 时直接丢弃。
恢复失败回到原 branch/tick 或明确 Faulted 并保持 Paused，随后统一清理输入与时间。
