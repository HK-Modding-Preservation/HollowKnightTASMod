# T08 暂停与受控步进验收报告

> **2026-08-08 superseded notice**：本报告证明的是旧版 `Controlled Step`
> endpoint 契约，不足以证明无 Mod 逐 tick 等价。T24 已用真实游戏反例证明：
> `Time.timeScale=0` 期间继续发生的 `Update/LateUpdate` 会让 animation/VFX/FSM
> 在两次单步之间前进，造成快速二段跳翅膀与 Hero 状态错位。T08 当前状态为
> `REOPENED_BY_T24`；新边界和候选证据以
> [`T24_原版执行语义逐帧等价门禁.md`](../specs/tasks/T24_原版执行语义逐帧等价门禁.md)
> 为准。下文保留为历史证据，不再单独支持帧级 TAS 声明。

## 结论

历史 T08 矩阵为 **PASS / VERIFIED（已由 T24 重新打开）**。Runtime 当时可以用显式状态机和
`Time.timeScale` lease 暂停 gameplay simulation；暂停期间 movie cursor
关闭，而 raw visual/input 更新仍被如实记录。单步能力只开放
`MovieTick` 边界，每个请求恰好消费声明数量的 movie tick。

正式产品名称判定为 **Controlled Step / 受控步进**，不得显示为
`Tick Step` 或通用“帧步进”。100 次单步中：

```text
visual/fixed/input delta = 1/0/1：79 次
visual/fixed/input delta = 1/1/1：21 次
movie delta = 1：100/100 次
```

fixed 增量并不恒定，所以它不是“一次请求等于一个 Unity fixed tick”。

## 交付

- Core：
  `SimulationControlMode`、`StepBoundary`、`StepRequest`、`StepResult`、
  `SimulationControlStateMachine`。
- Playback：
  `PlaybackStateMachine.DeclareRawInputSuspension()`，允许显式暂停造成的
  raw InControl tick 前向跳变；未声明跳变和倒退仍 fail closed。
- Runtime：
  `IMovieTickGate`、`TimeSettingsLease`、`TimeScaleGateStrategy`、
  `RuntimePauseController` 和 `RuntimeStepProbeExperiment`。
- Harness：
  `scripts/Invoke-T08StepMatrix.ps1`，隔离 profile 后逐进程执行
  pause/baseline/step/restore 矩阵并恢复普通 Mods。

`RuntimePauseController.Step()` 只提交异步请求；结果在 Unity
`LateUpdateEnd` 收口后由 `TryTakeCompletedStep()` 取得。它不会阻塞 Unity
主线程等待下一帧。

## Pause Test

两个独立进程都在 movie tick 20 暂停至少 5 秒墙钟时间：

| Profile | 时长 | Movie | Visual 增量 | Fixed 增量 | Input 增量 | 前后 verification hash |
|---|---:|---|---:|---:|---:|---|
| 静止 | 5.010520 s | 20→20 | 1178 | 0 | 1178 | 完全一致 |
| 左移中 | 5.017107 s | 20→20 | 1196 | 0 | 1196 | 完全一致 |

这证明的是 gameplay simulation 和 movie cursor gate，不是进程冻结：
`Update`、unscaled UI、输入扫描和墙钟仍可继续。

## Step Test

正常速度运行 100 个 neutral movie tick 与 100 次逐一授权的 Controlled
Step 使用同一 normalized baseline。两者 endpoint verification SHA-256
都为：

```text
ddf9fd7b744a70c568ea7d4ccb34ceedf31a2b89e0aa711949cf2f5de5ab1d8a
```

STEP 进程产生 101 条输入 observation（100 个 movie tick + 1 个 release
boundary），mismatch 为 0。100 份 `StepResult` 均含实际
movie/visual/fixed/input delta 和对应 ledger slice；完整 step ledger 共
435 条记录并通过 T03 `TickLedgerValidator`。

当前 endpoint parity 复用 T07 的 stationary grounded/idle oracle；它证明
受控步进没有改变该已验证路线的结果，不外推到移动、加载或 RNG 路线。

| 路径 | 触发证据 | Time settings exact-bit | Binding | Ledger |
|---|---|---|---|---|
| 正常 Resume | `resume` | PASS | PASS | PASS |
| 场景请求 | `scene-load-requested:GG_Workshop` | PASS | PASS | PASS |
| Focus loss | `focus-loss` | PASS | PASS | PASS |
| 受控异常 | `controlled-fault:t08-probe` | PASS | PASS | PASS |
| Mod shutdown | `mod-shutdown` | PASS | PASS | PASS |

对每条适用路径，`timeScaleBits`、`fixedDeltaTimeBits`、
`targetFrameRate` 和 `vSyncCount` 的 before/after 均完全相等。
`TimeSettingsLease` 只写本任务主动改变的 `timeScale`，没有重写
`fixedDeltaTime`、target FPS 或 vSync。

场景测试使用真实 `GG_Vengefly → GG_Workshop` 请求，并把
`SceneLoadRequested` 与 `ActiveSceneChanged` 写入 ledger。Focus profile
通过探针调用与 Unity `OnApplicationFocus(false)` 完全共用的处理器，验证
恢复逻辑和接线；本报告不把它描述成一次独立 OS 窗口焦点自动化实验。

## 命名与功能边界

- Runtime v1 支持 `MovieTick` Controlled Step。
- `VisualUpdate` 保留为协议枚举，但 Runtime 明确拒绝把它作为 simulation
  step；以后若实验证明语义稳定再单独开放。
- 不修改 `fixedDeltaTime`，不冻结线程/音频/网络，也不宣称与 libTAS
  等价。
- scene load request、游戏非 PLAYING、focus loss、异常和 shutdown 都先
  恢复时间 lease；恢复不等价时进入 `Faulted`，不能继续 step。
